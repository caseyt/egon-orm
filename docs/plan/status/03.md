One optimisation was made, with the benchmark that shows it. Reading a `"YYYY-MM-DD"`
string as a `Date` first used a regular expression, three `Number()` calls and `Date.UTC`:
128 µs per 1,000 values. It now reads character codes and computes the day count with
integer arithmetic: 57 µs, of which 28 µs is allocating the `Date`s. The same change took
the date cast from a string from 143 ns to 28 ns. A test checks the arithmetic against

character codes costs 11.4 µs and rejects everything that is not digits. A property test
(5,000 runs) checks it against `BigInt` across the 64-bit range.

## Decisions

Choices the spec left open. Each is covered by tests.

1. **The built-in types are functions named `<kind>Type`** (`integerType()`), exported
   from `types/index.ts` only. A type without options is one shared object.
2. **`IDENTITY` is not public.** `index.test.ts` (step 02) asserts that it is not
   exported. A custom type leaves `fromDb` and `toDb` out and `defineType` fills it in.
3. **`defineType` requires `fromDb` and `toDb` at the type level when `TDb` differs from
   `TApp`**, and lets them be left out when the two are the same. `TDb` defaults to `TApp`.
4. **`defineType` validates the definition** and throws `SchemaDefinitionError`: an empty
   name, a `cast` that is not a function, a `db` whose kind does not exist, or a `custom`
   `sql` that does not match `CUSTOM_SQL_TYPE` (so the mistake shows where the type is
   defined, before the compiler refuses it). The type keeps a frozen copy of `db`, so what
   was checked cannot be changed afterwards through the caller's object.
5. **A type's functions are kept apart from the type without breaking a hand-written
   one.** An array type holds its element's functions and `resolveCodec` returns `fromDb`
   and `toDb` on a new object, because wrapping them would add a call per value per row.
   The contract declares the members as methods, so a type written as a class may use
   `this`. `detached(type, member)` therefore returns the function itself for a type made
   by `defineType` (the guide tells authors not to use `this` there) and the function
   bound to the type, once, for any other type. `IDENTITY` is never bound. The contract
   is unchanged. (The first version of this PR called every type's functions without a
   receiver, which narrowed the contract; the reviewer caught it.)
6. **Every type has the same six properties in the same order** and is frozen. Nothing
   else is attached to a type. The element type of an array is kept in a `WeakMap`
   (`elementTypeOf`), and a decimal's precision and a timestamp's precision appear only in
   the type's `name`.
7. **integer**: safe integers, as the spec says, not the 32-bit range of the Postgres
   column. `-0` is returned as `0`. Strings longer than 40 characters are rejected before
   parsing.
8. **bigint**: the spec says "integer `number`". I accept only **safe** integers: a larger
   number has already lost digits, and storing a neighbouring value silently is worse than
   `is invalid`. Values outside the 64-bit range are rejected, as the column would.
9. **bigint `{ mode: "number" }`**: its `fromDb` accepts a number, a bigint or a digit
   string and throws `CastError` beyond the safe range. It handles the string itself
   because the range check has to see the driver's value whatever form it arrives in. A
   string that is not an optional `-` and digits throws `CastError` too.
10. **float**: numeric strings may have a sign, a fraction and an exponent; at most 400
    characters. `"NaN"` and `"Infinity"` are rejected.
11. **decimal**:
    - Strings may not have an exponent. Numbers that print with one (`1e21`, `1e-7`) are
      written out in full.
    - The result is in a normal form: no `+`, no leading zeros, no bare point, no negative
      zero. Fraction digits are kept as written (`"19.990"` stays `"19.990"`).
    - With `{ precision, scale }` the value is rounded to `scale` half away from zero,
      which is how Postgres rounds `numeric`, and padded to `scale`. A number with more
      than `precision - scale` digits before the point is rejected. `scale` defaults to 0,
      as in SQL. Rejecting extra fraction digits instead would have made `0.1 + 0.2`
      invalid for a two-digit column.
    - `equal` compares numerically (`"1.50"` equals `"1.5"`), because the database returns
      the column's scale and a changeset would otherwise see a change that is not one.
12. **boolean**: exactly the eight inputs of the table. `"TRUE"`, `"yes"` and `2` are rejected.
13. **date**: years 1 to 9999. The `{ year, month, day }` form accepts whole numbers or
    digit strings (form input). With `{ as: "date" }` the driver value is the
    `"YYYY-MM-DD"` string (`FieldType<Date, string>`): `fromDb` parses it to midnight UTC
    and throws `CastError` for `"infinity"` or a BC date; `toDb` writes the UTC date and
    throws `CastError` for an invalid `Date` and for one outside the years 1 to 9999, so
    that it never writes a date it could not read back.
14. **time**: normalised to what the database returns: seconds always present, no trailing
    zeros in the fraction.
15. **timestamp and localTimestamp**:
    - The spec's table says both "truncates to seconds unless `{ precision }`" and "default
      ms". I read it as: `precision` is `"s" | "ms" | "us"`, default `"ms"`.
    - `"s"` drops the milliseconds of accepted input (towards the earlier second, also
      before 1970). It does not touch `fromDb`.
    - `"us"` is a distinct type (`timestamp(us)`) that behaves like `"ms"`: a JavaScript
      `Date` cannot hold microseconds. It exists so that a column can be declared with
      microsecond precision. See "Known gaps".
    - Strings are matched against a grammar, never handed to `Date.parse`. The separator
      may be `T`, `t` or a space; seconds are optional; the offset may be `Z`, `±HH`,
      `±HHMM` or `±HH:MM`. Fraction digits beyond three are dropped.
    - A plain `Date` is returned as the same object. An instance of a `Date` subclass is
      copied into a plain `Date`, because its methods may be overridden and `equal` calls
      `getTime`. A number (epoch milliseconds) is rejected: the table lists only `Date`
      and strings.
16. **json**: "any JSON-serialisable value" is read as "any value JSON represents
    exactly". `undefined` inside a document, `NaN`, `Date`, `Map`, class instances,
    `bigint`, functions, cycles and nesting deeper than 500 are rejected, because they
    would be stored as something other than what was passed, or would throw in the driver
    at query time. This is a full walk of the document on every cast (184 ns for the
    4-key benchmark document), which is more than the spec's "no deep validation"; the
    shape `T` is still not checked. A container referenced from several places is walked
    once, and its height is remembered so that the depth limit gives the same answer
    wherever it appears. `cast` returns the same object, not a copy.
17. **array**: a `null` or missing element is rejected by `cast`, with its index (the
    element type has no way to say it is nullable, and `T[]` has no `null`). `fromDb`,
    `toDb` and `equal` pass a stored `NULL` element through without calling the element
    type. A failed element's `message` and `meta` are kept, and `index` and `path` are
    set: `path` holds the indexes that lead to the value (`[1]`, or `[1, 2]` in an array
    of arrays). Every array type writes `path` itself, so an element type's own `path`
    metadata is replaced, never extended.
18. **enum**: a mapping's values are all strings (`text`) or all whole numbers
    (`integer`), and distinct. A mapping in which a key is also the stored value of
    another key is rejected with `SchemaDefinitionError`: input may be a key or a stored
    value, so one spelling must not mean two members. `fromDb` of a value that is not in
    the mapping throws `CastError`. Every enum is named `enum`.
19. **`resolveCodec`** takes `Pick<Adapter, "typeOverrides">` and caches in a `WeakMap` per
    adapter object. For an array type that the adapter does not override, the element
    type is resolved through the adapter too and applied per element, so overriding
    `bigint` also fixes `bigint[]`. An override of the array type itself wins.
20. **`parameterized`** keys its cache on the options' content: plain objects whatever
    their key order (symbol keys included), arrays in order, primitives by value and type.
    A type, a function, a symbol or a class instance is compared by identity. Extra
    properties on an array are ignored. Options nested more than 100 deep, which in
    practice means options that contain themselves, throw `SchemaDefinitionError`.
21. **`deepEqual`** treats `0` and `-0` as equal (JSON cannot tell them apart), `NaN` as
    equal to `NaN`. Only plain objects are compared by their keys, whichever realm each
    was made in and whether or not it has a prototype: a `Map`, a `Set` or a class
    instance is equal only to itself. "Plain" is `internal/plain-object.ts`: no prototype,
    or the `Object.prototype` of some realm.
22. **Values from another realm are accepted** where the built-in types look at an
    object: a `Uint8Array`, a `Date` and a plain object made in another realm (a Jest
    test environment, a `vm` context) pass, as arrays always did. The checks read
    internal slots instead of using `instanceof`, which is also what keeps them from
    running a hostile value's code.
23. **No error message contains the offending value**, since the field may be redacted.

## Review, round 1

taken:

- Decision 5 narrowed the frozen `FieldType` contract. Replaced by `detached` (see 5).
- Guide changes are now listed for the owner (the section above).

## Review, round 2

The reviewer confirmed all fourteen round-1 findings resolved and found six more in the
code added in round 1. All were taken:

- The json depth limit depended on walk order when a container was shared. The walk now
  remembers each container's height.
- The test for "a plain object of any realm" accepted any object whose prototype had no
  prototype. It is now `isPlainObject` in `internal/plain-object.ts`, used by the json
  cast and by `deepEqual`, which compares two plain objects whichever realm each is from.
- An element type's own `meta.path` could be spread into, or break, the path of an array
  of arrays. Every array type now writes `path` itself.
- The frozen copy of an array column type had no test. Added.
- `defineType` read `db.kind` several times. Each property is now read once.
- Three guide changes were missing from the table above. Added.

## Known gaps

- `t` does not exist yet (first Acceptance box).
- `timestamp({ precision: "us" })` cannot carry microseconds. Reading a
  `timestamptz(6)` value into a `Date` drops them, so a row written back loses them. A
  type that keeps them would need another application type than `Date`.
- `integer` accepts values beyond the 32-bit range of a Postgres `integer` column. Such a
  value fails in the database, not in the changeset.
- Casting a timestamp from an ISO string costs about 300 ns, most of it the regular
  expression. I did not hand-write that parser: the grammar has several optional parts, and
  no budget is at risk from it yet.
- Nothing here ran against a database. That each driver produces and accepts the
  representations listed under "Requests" is for steps 11 and 17 to verify.

## Requests

**Step 04 (schema)**

- Wrap the functions in the table above. `t.array(inner)` passes the inner builder's type
  to `arrayType`; `t.type(custom)` takes the type as it is.
- A builder has to expose its `FieldType` to `param`, `expr.cast` and schemaless changesets.
- Convert the two remaining hand-written blocks of `guide/types.md`.
- Once `t` is public, the benchmarks can use it and the `types` re-export in
  `internal/index.ts` can be removed.

**Step 05 (changeset)**

- A failed cast may carry `message` and `meta`; an array's failure has `meta.index`.
- Cast results can be shared frozen objects (`INVALID`, both boolean results, every enum
  result). Do not mutate a `CastResult`.
- `equal` for `decimal` is numeric, and for `json` structural.

**Steps 10 and 12 (compiler, repo reads)**

- Get conversions from `resolveCodec(type, adapter)`, once per column per plan. The
  returned object is frozen and its functions are safe to call without a receiver; skip
  the call when the function is `IDENTITY`. To keep any other function of a type apart
  from the type, take it with `detached(type, member)` from `types/define.ts`.
- `fromDb` may throw `CastError` (`bigint(number)`, `date(date)`, a mapped enum).

**Steps 11 and 17 (adapters)**

- The representations the types expect from a driver, and hand to it:

  | `db.kind` | Driver value |
  |---|---|
  | `integer`, `float` | `number` |
  | `bigint` | `bigint` for the `bigint` type. `bigint(number)` reads a number, a bigint or a digit string by itself. |
  | `decimal` | `string` |
  | `boolean` | `boolean` |
  | `text`, `uuid`, `time` | `string` |
  | `binary` | `Uint8Array` (a `Buffer` is one) |
  | `date` | the `"YYYY-MM-DD"` string, for both `date` types |
  | `timestamptz` | `Date` |
  | `timestamp` | a `Date` whose **UTC** fields are the wall time |
  | `json`, `jsonb` | the parsed value |
  | `array` | a JavaScript array, `null` for a `NULL` element |

- For `pg` that means: `int8` needs an override for the `bigint` type (text to `BigInt`);
  `date` must arrive as the raw string (the default parser builds a local-midnight
  `Date`); `timestamp` without a time zone must be read as UTC (the default parser reads
  it in the process's zone); a `json` parameter must be serialised by the adapter (`pg`
  writes a JavaScript array as a Postgres array literal and a bare string as text).
- An override replaces the type's own conversions, it does not wrap them. So dispatch on
  the type and not only on `db.kind`: `bigint` and `bigint(number)` share a kind, as do
  `date` and `date(date)`, and an override meant for the first would break the second.
- Override element types, not array types, unless the dialect has no arrays:
  `resolveCodec` applies an element's override to each element.

**Step 18 (migrations)**

- A decimal's precision and scale and a timestamp's precision are only in the type's
  `name`. If migrations need them as data, the place for them is a lookup beside
  `elementTypeOf`, not a property on the type (decision 6).

**Benchmarks (step 19)**

- `dist/internal.js` is bundled apart from `dist/index.js`, so it has its own `IDENTITY`
  and its own registry of defined types. A benchmark must take everything from one of the
  two files. Mixing them still gives right answers, but loses the `IDENTITY` skip and
  makes `detached` bind functions it would otherwise return as they are.

Branch `fix/consumer-types`, 2026-10-20. A fresh-eyes docs test installed the built
packages into a clean consumer project and found five problems. This note sits in step
03's file because the types own two of them: the declarations a consumer's schema classes
need (TS2883), and what `t.integer()` and `t.float()` hold after a read. The fixes touch
files that belong to other steps too: `contracts/schema.ts` exports (04), the decoder
`repo/hydrate.ts` (12), the migration builder (18), and the build and smoke test (01).

### What changed

1. **TS2883 in a consumer with `declaration: true`.** `export class User extends
   Schema("users", {...}) {}` failed because the inferred class type mentions
   `DefaultFieldFlags` and `WithFlag`, which no public entry exported. `egon-orm` now
   exports, as types, `DefaultFieldFlags`, `WithFlag`, `LoadedUnchecked` and
   `FieldFlags`. The first three are needed: the consumer check fails with TS2883 without
   each. `LoadedUnchecked` was found by the check itself: an exported query with a nested
   preload (`from(Post, "p").preload({ author: ["profile", "groups"] })`), and
   `repo.oneOrThrow` of one, have inferred types that mention it. `FieldFlags` is not
   needed by any inferred type (the check passes without it; review round 1). It is exported
   because it is `WithFlag`'s constraint, which a consumer naming `WithFlag<F, K>` needs,
   and public signatures such as `val` and `param` mention it. All four had TSDoc with an
   example; `LoadedUnchecked`'s was rewritten for consumers in review round 1.
   - To find what was missing, the consumer check compiles `examples/smoke/types/consumer.ts`,
     a file of about 120 exported declarations with inferred types. It covers schemas with
     every field builder and modifier, embeds, every kind of association, custom and
     parameterized types, changesets including nested ones and embeds, `toZod` and
     `castWith`, queries (joins, preloads, subqueries, CTEs, windows, set operations,
     dynamic conditions, `prepare`, bulk `set`/`returning`, locks), most repo methods,
     batches, the sandbox and migrations. While I worked on it I also compiled every
     `docs/site/examples` file except `testing.ts` (vitest) and `egon.config.ts` (the
     private CLI package) this way, in a throwaway consumer. They need nothing beyond the
     same four types.
   - A script that walks the built `.d.ts` lists 284 declarations that public declarations
     mention but no entry exports, nearly all AST nodes and conditional helpers that tsc
     resolves before it writes a consumer's declarations. I did not export those: only what
     an inferred type needs, plus `FieldFlags` (above), is exported (owner row 5).
2. **TS2637 in the shipped `.d.ts`.** The cause was not `Expr` or `OrderExpr` themselves:
   their variance annotations on a class are valid. It was `src/internal/index.ts`'s
   `export * as expr from "../query/expr.js"`. To build declarations for the
   `dist/internal.js` entry, the bundler wrote namespace aliases into the shared chunk,
   such as `type expr_Expr<out T, in P = NoParams> = Expr<T, P>`. tsc rejects a variance
   annotation on an alias of a class (three errors). `dist/internal.js` needs no
   declarations: it is not in `exports`, it is left out of the published files, and the
   benchmarks take its types from the sources. So `packages/core/tsup.config.ts` now
   builds declarations for the three public entries only (`dts.entry`). The chunk no
   longer has the aliases, and `dist/internal.d.ts` is no longer written (owner row 4).
3. **TS7016 for `pg`.** `@egon-orm/postgres`'s `.d.ts` imports `pg` for `pg.Pool` (the
   `pool` option takes an existing pool) and `pg.ConnectionConfig["ssl"]`. `pg` ships no
   types. Decision: **`@types/pg` is an optional peer dependency** (`^8.23.0`, like `pg`,
   with `peerDependenciesMeta`) (owner row 1). I checked the others. `pg-cursor` appears
   in no published `.d.ts`. `mysql2` ships its own declarations (the MySQL `.d.ts` imports
   `SslOptions` from it; they need `@types/node`, as any Node project has). Neither the
   SQLite nor the Zod `.d.ts` imports `better-sqlite3`, and `zod` ships its own types. No
   change was needed for those.
4. **A `t.integer()` field over a `bigserial` column held a string.** `pg` reads `int8`
   (and `numeric`) as text. The Postgres adapter has no driver codec for the `integer`
   kind, and `integerType()`'s `fromDb` is the identity, so the decoder skipped the field
   and passed the string through. `t.float()` over `numeric` did the same. Now the decoder
   checks every `t.integer()` and `t.float()` value. The check is made once per value of
   the plan when the decoder is built (`numberCheck` in `repo/hydrate.ts`), and it runs on
   the value after the dialect's driver codec. A value that is not a `number` throws
   `CastError`. The error names the field (`User.id`, or the key path of a selected object,
   `"stats".posts`; a write's returned row is named by its schema) and the kind received,
   says what that means without assuming a database ("the column or expression is not of
   an integer type", then what Postgres and MySQL do), and suggests
   `t.bigint({ mode: "number" })`, `t.decimal()` or another column type. When the row came
   back from a write it adds that the write was applied. The message never includes the
   value (the field may be redacted). How it depends on the dialect:
   - Postgres: `int2`/`int4`/`float4`/`float8` arrive as numbers and pass. `int8` and
     `numeric` arrive as text and throw.
   - MySQL: its `integer` codec turns digit text into numbers, and its `float` codec
     numeric text, so `t.integer()` over a `bigint` column reads numbers there (an
     integration test shows it). Numeric text with a fraction is not converted for
     `t.integer()` and throws. That is what MySQL's `/` returns: **`p.views.div(2)` on a
     `t.integer()` column now throws on MySQL** (`"3.5000"`), where Postgres and SQLite
     give `3`. Before, it was the string `"3.5000"` typed `number`. A `t.integer()` over a
     MySQL `decimal` column throws the same way. (Corrected in review round 1; the first
     version of this note said only non-numeric text throws.) Pinned by a MySQL integration
     test; owner rows 2 and 6.
   - SQLite: integers arrive as `bigint` and its codec makes them numbers. Text stored in
     an integer column (SQLite allows that) now throws instead of leaking.
   - Cost: where no conversion applies (Postgres), the generated decoder tests
     `typeof v === "number"` inline and calls nothing for a number. Where a driver codec
     applies (MySQL, SQLite), the check is a second call on the converted value. The check
     functions are made when the decoder is built, never per row. No benchmark was run
     (step 19).
   - Values the library selects itself were already typed so that they pass: `count`,
     `sum` over integers, `rowNumber`/`rank` read as `bigint({ mode: "number" })`, and
     `avg`, `percentRank` and `cumeDist` are cast to float. All suites pass unchanged
     (see Verification).
   - This is a behaviour change (owner row 2).
5. **`t.id({ type: "integer" })` in a migration.** It failed at compile time and at run
   time; only `t.id("id", { type: "integer" })` worked. I added the overload
   `t.id(options?)`: options as the first argument when the key is named `id`. The old
   forms are unchanged, including `t.id(undefined, options)`. Options given twice
   (`t.id({...}, {...})`) throw a `TypeError`. The options type is now named and exported
   from `egon-orm/migration` as `IdOptions` (owner row 3).

  whether its bound operands and the quotient are cast to the integer type (as after review
  round 1).
  - Postgres: `/`, no cast. Its SQL is unchanged.
  - MySQL: `div`, no cast: `` `p`.`views` div ? ``.
  - SQLite: `/`, with the bound operands and the quotient cast,
    `cast("p"."views" / cast(? as integer) as integer)`.
- **The emitter chooses it when the plan is made** (`compiler/emit.ts`: `integerQuotient`,
  `numericTypeOf`, `arithmeticType`, `quotient`). It applies when both operands of `div` are
  known to be integers, meaning `integer` or `bigint`, the first two places of the
  widening order in `query/widen.ts` (`numericRank`). A typed `p.views.div(…)` result is
  then an integer type, so the database now returns what the decoder expects.
  - What counts as known: a column of a schema's field (`columnType`), a typed value, a
    cast, an integer literal, `count` (a bigint on every database; review round 1), unary
    minus, and arithmetic of those (the wider of the two, by the same order). A value bound
    without a type takes the other operand's type, as the database reads it.
  - Anything else keeps `/`: a float or decimal operand, a fraction literal, a custom type,
    a function, another aggregate (Postgres's `sum` of a bigint is a `numeric`), a fragment,
    or a column whose type is not known (a `values` source, a subquery that selects values).
  - There is no dialect-name check (`check-dialect-conditionals` passes). The decision
    depends on the node kinds, the types (compared by identity in the plan's shape) and the
    literal values (in the shape too), so it is cached with the plan.
- **SQLite.** Probed through the read conformance and `sqlite.itest.ts`: with no cast,
  `"p"."views" / ?` gives 3.5 (better-sqlite3 binds every JavaScript number as a `real`,
  the gap in status 10's column-type follow-up). The first version cast only the quotient,
  which truncates towards zero but still divided a real: above 2^53 it was off by one
  (review round 1, finding 1). Now the bound operands are cast too, so SQLite divides two
  integers exactly, and the quotient cast stays for a real stored in an integer column. I
  chose casts over binding safe integers as `BigInt` in the adapter: that would change how
  every integer value is bound, in every statement, not only in a division. All three
  databases now agree on `p.views.div(2)`, and on 2^60 − 1 divided by 1024.
- **A `t.integer()` value must be a whole number** (review round 1, finding 3; owner row 7
  below). `compiler/bind.ts` exports `wholeNumber`, one shared function that the compiler
  gives every slot of the built-in `t.integer()` type in place of the identity
  (`compiler/emit.ts`, `toDbOf`). A number that is not a whole number (a fraction, `NaN`,
  an infinity) throws `QueryError` when the query is bound. `bindParams` names the slot:
  "Parameter 2 …", "The named parameter "minAge" …", or "An item of parameter 1 …" for a
  bound array. Whole numbers, `null` and digit text pass unchanged. The function is the
  same for every plan, so plans compiled twice still compare equal (the determinism test);
  the slot is named on the failing path only. Cost: one call per `t.integer()` value per
  execution, where the identity was skipped before (no benchmark; step 19).
- Also resolved: status 10's Known gap "New with the widening, on MySQL and SQLite".
  `p.views.div(val(2, t.bigint({ mode: "number" })))` divides as integers on both now (the
  read conformance asserts 11 for 45 / 4).
- `query/expr.ts` (step 07): the `div` TSDoc now says two integers divide as integers on
  every database, written `DIV` on MySQL (status 10's Request for that sentence).

### Known gaps

- A `div` whose operand type the emitter cannot see keeps `/`, so on MySQL it still gives a
  decimal. Examples: an aggregate other than `count` (`sum(p.views).div(2)`), a function
  (`coalesce`), a fragment, a column of a subquery that selects values. A `t.integer()`
  result of such a division still throws there. Workaround, in the guide: cast the operand,
  `sum(p.views).cast(t.integer()).div(2)` (the read conformance runs it on all three: 82).
- **Division by zero differs** (review round 1, finding 5), unchanged by this PR: Postgres
  refuses it (22012); SQLite gives `null`; MySQL gives `null` in a select and refuses it in
  an `UPDATE … set n = n div 0` (1365, strict mode). The guide says so.
- SQLite: only the bound operands of the division itself are cast. A bound value inside
  nested arithmetic (`x.b.add(1).div(1024)`) is still a real, so above 2^53 that sum is
  inexact before it is divided. That holds for SQLite arithmetic in general (status 10,
  Requests: SQLite binds every number as `real`); not changed here.
- The whole-number check covers the built-in `t.integer()` and `t.bigint({ mode:
  "number" })`; a custom type with an integer column is not checked (owner row 7).
- A write names the field only for values bound one per field. An `update`'s key or lock
  value (from a loaded row) and a conflict value keep the error that names the parameter.
  Two defensive branches are not covered by a test: such an `insert` value past the
  columns (`bindFields`), and an `updateAll` root without schema metadata (`setFieldAt`).
