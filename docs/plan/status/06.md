## Decisions

1. **`~standard` is checked before "is a function".** ArkType's schemas are callable, so
   the spec's order (a function is a validator function) would call them as one. A value
   with a `"~standard"` property is a Standard Schema; a `"~standard"` that is not a version-1
   object with `validate` is a `TypeError` (no fallback). `"~standard"` is read once (Yup
   defines it as a getter).
2. **Errors for misuse.** A value that is not a validator: `TypeError` naming what it got
   (spec). A promise from `validate`: `QueryError` with the spec's message;
   `validateField` says `use validateFieldAsync`. A bad option, an unknown field in `only`
   or `validateField`, `apply` with a function: `QueryError` (as in step 05). A malformed
   issue from a function, or a Standard Schema result that is not one: `TypeError`.
   The async variants reject instead of throwing.
3. **A promise refused by `validate` gets a no-op rejection handler**, so a rejecting
   async validator does not also raise an unhandled rejection.
4. **Fields with no value are left out of the values object**, not set to `undefined`. A
   new record's field without a change or a default has no value; leaving the key out lets
   optional keys accept it in every library (ArkType's and Zod's `exactOptional` keys
   reject an explicit `undefined`) and lets required keys report it as missing.
5. **`ctx.data`** is the row for a loaded row, the data object for a changeset without a
   schema class, and for a new record a frozen object of every field's default
   (`undefined` where there is none). The values before the changes are computed once per
   validation and shared by the values object and `ctx.data`, so a default given as a
   function is called once (review round 1). `ctx.isChanged` is a closure, so
   destructuring it works.
6. **`scope: "changed"` keeps issues on `BASE`**: those with an empty path and those whose
   first segment is not a field (an issue on a key that is not a field cannot be "unchanged").
7. **`only`** narrows the object (spec) and the issues (guide): an issue on a field outside
   the list is dropped; issues on `BASE` are kept. Names are checked.
8. **`apply`** needs a Standard Schema (a function has no output; it throws). It runs only
   when the schema returned a value (no issues). For each output key that is a field, the
   value is first cast with the field's type, as `cast` casts input; a value the type
   rejects becomes a `cast` error on the field (`validation: "cast"`, `meta.type` and the
   type's own meta) and is not written (review round 1). A cast value that differs by the
   field's type from the field's current value is set with `putChange`, so a value back
   to the row's removes the change, and `null` on a field that is not nullable gives
   `can't be blank`. `undefined` output values are skipped. An embed field whose output
   differs throws, as `putChange` does (embeds are changed with `putEmbed`, step 15).
   **`apply` with `only` or `scope: "changed"` throws `QueryError`** (review round 1): a
   Standard Schema that reports any issue returns no output, so when those options drop
   the issues afterwards the changeset would be valid with its transform silently not
   applied. Applying "for the permitted fields" is not possible without an output.
9. **`validateField`** skips a change to `null` as well as no change, like the built-in
   validations. Its function form receives `(value, ctx)`; issue paths are relative to
   the value (`[]` for the value itself) and go to `meta.path`. It records
   `[field, { schema: validator }]` whether or not it ran.
10. *(Superseded after merge: see "Owner decisions after merge".)*
    **A function's result that is not a list means no issues**, as the contract's
    `ValidatorResult` documentation says; an element that is not `{ message: string, … }`
    throws. **Open question for the owner** (review round 1, not changed here): a function
    that returns a single issue object (`() => ({ path: "email", message: "bad" })`, a
    forgotten pair of brackets) or a string leaves the changeset valid. Should a non-list
    result other than `undefined` throw a `TypeError`? That changes the contract's
    `ValidatorResult` TSDoc, so it is left to you.
11. **Paths are stored as plain arrays.** ArkType reports an array subclass with an extra
    `cache` property; such a path is copied. A plain array of keys is used as given.
12. **Error shape**: `{ message, validation: "schema", meta: { path: rest, ...issue.meta } }`,
    in that order (an issue's own `meta.path` would win, as the spec writes it). `BASE`
    errors keep the whole path. Errors are appended after existing ones in issue order;
    `cs.changes` is the same object after a failing validator.
13. **Yup.** Its Standard Schema is async-only (`async validate`), so it works with
    `validateAsync`; for synchronous use the guide documents a 12-line adapter that calls
    `validateSync` and returns issues (tested). The spec allowed the adapter for a Yup
    without Standard Schema; this is the async-only variant of that case.
14. **Values built by generated code** (one function per field table, cached), with a loop
    fallback when `new Function` is refused (a CSP without `unsafe-eval`). A test loads the
    modules with `Function` stubbed to throw and checks both builders give the same values.
15. **`toZod` row mode infers `FieldValues<S>`** (the fields of the row) rather than
    `Row<S>`: a Zod object yields a plain object and cannot carry the class's getters and
    methods. For a class without them the two are equal (type-tested). `"update"` is every
    field optional, virtual fields included; `"insert"` follows `InsertShape` (no virtual
    fields). Optional keys use Zod's `exactOptional`, which arrived in Zod 4.3: the peer
    range is `^4.3.0` (it was `^4.0.0` in the placeholder).
16. **`toZod` field mapping** (reworked in review round 1). Every field accepts exactly the
    values its type holds, checked with the type's own `cast` and `equal` (enum members,
    decimal scale, timestamp precision, lower-case UUIDs, safe integers). The check also
    requires the same kind of value (same `typeof`; for objects, an instance of what the type produces, so a `Date` subclass passes; review round 2),
    because a type's `equal` is only defined on its own values: the decimal type's calls
    the number `12.5` equal to `"12.50"`. The built-in scalar types are recognised **by
    identity**, not by name or column kind: `toZod` declares a private embedded schema
    with `t.string()`, `t.integer()`, … (every precision of the timestamps) and reads the
    type objects from its metadata, so a custom type named `"string"` or stored in a
    `timestamptz` column can never be mistaken for a built-in one. Those get a Zod base
    (`z.string()`, `z.int()`, `z.bigint()`, `z.number()`, `z.boolean()`, `z.date()`,
    `z.instanceof(Uint8Array)`), refined with the check, so a value of the wrong kind gets
    Zod's own message. Everything else (enums, arrays, decimals with a precision, JSON,
    custom types) is `z.custom(check)`. Messages are `is invalid` (`is not a valid UUID`
    for UUIDs). Enums are not `z.enum([...])` and arrays not `z.array(inner)` because
    core's public API does not expose an enum's members or an array's element type (see
    Requests); embeds are a lazy nested object.
17. **The zod hint** is a `zod` property on a `FieldType` (a Zod schema or a function
    returning one). `defineType` keeps only the members it knows, so the hint is added by
    spreading its result; the guide shows this. A hint that is not a Zod schema throws.
18. **`toZod` returns the same object for the same schema and mode** when there is no
    `pick`/`omit` (cached per class); embeds use the cached row object through `z.lazy`.
    `pick` and `omit` are checked at run time as well as typed: an unknown mode, or a name
    that is not a field of the mode (a virtual field in `"insert"` mode, say), throws
    `QueryError`.
19. **`castWith`** has the same overloads as `cast` (class, changeset, row alone,
    class-or-row union); every key of the Zod object must be a field, checked by the types
    and by `cast` at run time. It takes a `z.ZodObject` only (`TypeError` otherwise).
20. **`validate`'s values are typed `Readonly<FieldValues<S>>`** (spec), although a new
    record's field without a value is absent and `only` narrows the object. Typing them as
    partial would make the cross-field example need non-null checks.

## Known gaps

- `toZod` maps enums, arrays and decimals with a precision to `z.custom()` checks, not
  `z.enum([...])` / `z.array(inner)`: validation is exact, but a JSON Schema generated from
  them is coarse and their messages are `is invalid` (decision 16, Requests).
- The 2-issue Zod benchmark (`cs.validate(zodObject)`, 2 issues) has measured between +13%
  and +19% over calling Zod directly across runs, against the 20% target. It is the row
  most likely to trip step 19's regression gate.
- `validateField` with a failing schema is 33% over calling Zod directly (175 ns: the error
  objects and the new changeset). There is no target for it.
- Issues inside an association or embed stay on the field with the rest of the path in
  `meta.path`; routing them into nested changesets is step 15.
- `validate` does not check a Standard Schema's input type against the changeset's fields
  (a misspelled key in a Zod object is not a compile error).

## Review, round 2

The reviewer verified round 1 and raised three non-blocking points and one addition to
the Known gaps. All were taken; item 5 of round 1 stays with the owner.

1. **The kind check rejected a `Date` subclass that `cast` accepts.** An object now
   passes when the cast value's prototype is on its prototype chain (`isPrototypeOf`); the
   `typeof` check stays, so `12.5` against a decimal's `"12.50"` is still rejected (its
   test is unchanged). A test with `class MyDate extends Date {}` on `t.timestamp()`,
   `t.timestamp({ precision: "us" })` and `t.date({ as: "date" })` checks that `cast` and the
   schema both accept it; going back to an exact prototype comparison fails it.
2. **Two entries of the built-in table were untested.** A table-driven test now covers
   every entry (18 types): a value it holds passes, a value of the wrong kind gets Zod's own
   message (so a type that fell back to `z.custom` would fail), and, where the type can
   reject a value of the right kind, the refinement's message (`is not a valid UUID` for
   UUIDs, `is invalid` otherwise). Dropping `timestampUs` from the table and changing the
   UUID message each fail it.
3. **Nothing kept the guide's `yupSync` and the test's copy identical.** Both are now in a
   `yup-sync` region, and a test compares the text of the two regions (the zod package's
   project cannot import the docs example, which lives in another composite project).

## Owner decisions after merge

One decision in this note was changed by the owner after PR #15 merged, in a follow-up PR.

1. **A validator function's result that is not a list throws a `TypeError`** (replaces

   synchronous `validate` is still refused with `QueryError` first.

     row for decision 10 in the guide table above is struck through and states this rule.
   - Tests: every non-list kind in sync, async and promise-resolving forms, for both the

     message; arrays and `undefined` still pass. Turning the throw into "no issues" fails

## Follow-up: one error per field

Branch `fix/one-error-per-field`, 2026-10-20.

**Owner decision (2026-10-20).** A field that already has a cast error must not get more
errors from a schema validator: users see one message per field. The case found: `cast`
turns `name: ""` into `null` and reports `can't be blank`; the Zod schema then sees no
`name` and adds `Invalid input: expected string, received undefined`, so the result was
`{ name: ["can't be blank", "Invalid input: …"] }`. It is now `{ name: ["can't be blank"] }`.

**This overrides two approved rules for fields that already have an error:** §11's
"`.validate()` keeps **every** issue by default" and decision 12 / the guide row "errors
are appended in issue order". Both still hold for fields without an earlier error and for
`BASE`; `scope` still decides which of the remaining issues are kept.

### What changed

1. **`validate` / `validateAsync`** (`validators/validate.ts`, `mapIssues`): an issue
   whose path starts at a field that already has an error (from `cast`, `change`,
   `putChange`, `validateRequired`, a built-in validation, `addError` or an earlier
   validator) is dropped, whatever the rest of its path. The check is one `Object.hasOwn`
   on `changeset.errors`, the errors from before the validator ran; no array is built.
   Under `scope: "changed"` the rule applies first, then the scope.
2. **Nested changesets.** Routed issues are mapped by the child's own `mapIssues`, so the
   rule applies to the child's field: `["pages", 0, "text"]` is dropped when that page's
   `text` has an error, and `["venue", "spot", "lat"]` when the nested embed's `lat` does.
   An issue on the nested key itself (`["venue"]`, `["cover"]`), which would go to the
   child's `BASE`, is dropped when the parent already has an error on that key (review
   round 1; routing runs before the field check, so this needs its own check).
3. **`BASE` keeps every issue** (it is not a field), and so does a key that is not a field.
4. **Within one validator run, a field without an earlier error keeps every issue the
   validator reports on it** (Zod's `z.string().min(3).email()` on `"ab"` still gives two).
   The decision was about errors that came before; see owner row B.
5. **`apply`**: an output value the field's type rejects adds no `cast` error to a field
   that already has one (it is still not written).

### Decision: built-in validations follow the same rule (item 3)

**Decided: yes, for consistency.** One message per field, the first failure, whatever
produced it. This changes approved step 05 behaviour (owner row A):

- `validateFormat`, `validateInclusion`, `validateExclusion`, `validateSubset`,
  `validateLength`, `validateNumber`, `validateConfirmation` and `validateAcceptance` add
  no error to a key that already has one (the check is in the shared `#check`).
  `validateConfirmation` and `validateAcceptance` check their own key
  (`passwordConfirmation`, `termsOfService`): an error on `password` does not stop
  the confirmation being checked.
- `validateChange` and `validateField` / `validateFieldAsync` **do not call** their
  function or schema for a field that already has an error (so a remote check is not made
  for an email that is already invalid). The validation is still recorded in
  `cs.validations`, as it is when the field has no change.
- `validateUniqueAsync` (`repo/write.ts`) already skipped when one of its fields had an
  error; it now also skips, without asking the database, when its error key (`errorKey`,
  by default the first field) has one (review round 1).
- The validations still check their arguments and still throw for a change of the wrong
  type (`validateLength` on a number), as before.
- Unchanged: `validateRequired` already skipped such fields (step 05 decision 11).
  `addError` always adds (it is an explicit call), `putChange(field, null)` still adds
  `can't be blank`, `merge` keeps both sides' errors, and constraint errors come from the
  database after a write that only happens when there are no errors.

Before this change, `cast(User, { name: "X" }, ["name"]).validateLength("name", { min: 2 }).validateFormat("name", /^[A-Z]{2}/)`
reported both messages; now only the length.
