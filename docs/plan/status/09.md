## Decisions

The ones marked **(sign-off)** change what a user sees and are in the table below.

1. **Where the query methods live.** `union`, `withCte`, `windows`, `set`, `returning`
   must be methods of `Query` (they need its private per-property counts), so they are in
   `builder.ts`, with their nodes and checks in `query/advanced/` (modules the builder
   imports and that do not import it back). Step 08's request asked for exactly this
   (`#next` and `patched` for `COMBINATIONS`, `CTES`, `WINDOWS`, `UPDATES`).
2. **(sign-off) Set operations: only the combined rows' clauses may follow.** After
   `union` (and the others) only `orderBy`, `limit`, `offset`, more set operations,
   `withCte` and `schema` may be added; anything else (`where`, `join`, `select`, `lock`,
   `preload`, `set`, …) is a `QueryError`, because in the AST it would apply to the left
   side only, silently. And the left side may not already have `orderBy`, `limit`,
   `offset` (they would come to apply to the combined rows) or a lock; neither side may
   have preloads or `set`. The alternative, letting other clauses apply to the left side,
   is the less explicit reading.
3. **(sign-off) Set operations: the two sides must select the same shape, keys in the
   same order, and no plain values**, checked when the query is built. Columns are
   combined by position: `{ a, b }` with `{ b, a }` has the same TypeScript type and would
   pair `a` with `b`; and a plain value is never sent to the database, so the left side's
   value would be returned for the right side's rows.
4. **(sign-off) Window names are declared before use.** The query type gains a fifth
   parameter `W` (the declared window names, `never` by default; `QueryWith` scopes have
   `string`). `over("w")` now types its result with a `UsesWindow<"w">` mark (a type-only
   change in step 07's `functions.ts`), and `select`, `selectMerge` and `orderBy` refuse a
   name not in `W` at compile time; at run time the same clauses refuse it with a
   `QueryError` (also for a name inside an expression the type cannot see, such as
   `rank().over("w").add(1)`). `exclude("windows")` is refused while a select or order
   still uses a named window, and resets `W`.
5. **(sign-off) Window functions need `over()`.** `rowNumber()` and the rest are typed
   `WindowFunction<T>` (an `Aggregate` with a type-only `NeedsWindow` mark) until `over`
   is called; `select` and `orderBy` refuse them without a window, at compile time and with
   `QueryError`, and refuse `filter()` on them with a `QueryError` (Postgres has none
   for these; this one is not a compile error). They are new
   entries of the compiler's aggregate table (decision 18 of step 10).
6. **Window function types.** `rowNumber`, `rank`, `denseRank` return 64-bit integers,
   read as `number` (like `count`); `percentRank` and `cumeDist` are floats; `ntile` an
   integer; `lag`, `lead`, `firstValue`, `lastValue`, `nthValue` keep their argument's type
   (`| null` for `lag`, `lead` and `nthValue`, unless `lag`/`lead` have a non-null default).
7. **(sign-off) `dynamic` has two forms.** `dynamic<{ u: typeof User }>(fn)` is the form
   in the guide; TypeScript cannot infer the callback's result when a type argument is
   given, so this form takes conditions without named parameters (a named parameter in it
   does not compile, so a requirement is never lost). `dynamic({ u: User }, fn)` infers
   everything (named parameters, order items, select shapes) and checks the bindings when
   the query runs the callback (`QueryError` for a missing binding or another schema). A
   dynamic expression is a function from bindings, so every clause that takes a callback
   takes one with no change to the builder; the binding type is `Binding<S, boolean>`, so
   it fits a nullable (outer-joined) binding too.
8. **`field(binding, name)`** with a literal name is typed as that column; with a `string`,
   as the union of every column's value type. Any name that is not a column throws.
9. **(sign-off) `scalar(q)` is `T | null`**: a scalar subquery with no row is `NULL`.
   It must select one expression.
10. **(sign-off) A source's binding.** A subquery or CTE that selects an object of
    expressions gives a binding with one column per key (a `SubqueryBinding`, columns
    typed like the selected values, all nullable on the optional side of an outer join);
    one that returns whole rows of a schema gives the schema's binding. Anything else does
    not compile (`SourceCheck`) and throws. A `selectedAs` name in such a select is the
    column's name in SQL. A redacted value stays redacted through a source (a value
    compared with `s.hash` is hidden from logs when `hash` is `u.passwordHash`).
11. **A query with no select over an object source returns its objects** (the guide's
    `from(subquery(postCounts), "c").where(…)`). This needed a small addition to
    `compiler/plan.ts` (below): before, it was a `QueryError`.
12. **(sign-off) `set` and `returning`.** `set` takes an object or a callback; plain values
    are bound with the field's type and redaction; `null` for a field that is not nullable,
    `undefined`, a virtual field or an unknown key is refused (types and `QueryError`); a
    later `set` adds fields and replaces repeated ones in place. `select()` on a query with
    `set` is a `QueryError` pointing at `returning()`; `set` on a query with a `select()`
    is refused too (it would be written as `RETURNING` without saying so), while
    `returning()` then `set` is fine. A delete query is a query without `set`; its
    `returning` is its select. The root must be a schema's table.
13. **Untyped values in `set`** (the owner's option A): an `Untyped` value (`val(5)`, a
    `CASE` of untyped values) does not compile as a `set` value or in `returning`
    (`SelectTypes`, as step 10 asked). A plain value takes the field's type, so this only
    concerns `val()` without a type.
14. **(sign-off) `prepare(q)` compiles on first run, not eagerly.** A plan depends on the
    adapter (dialect and driver conversions), which `prepare` does not have. The prepared
    query compiles the first time it runs on an adapter and keeps that plan (other
    adapters, operations and database schemas get one each), so later runs skip even the
    cache lookup. Deviation from "eagerly lowers": noted below.
15. **Tuples.** `tuple(...)` is not an expression; its comparison methods (`eq`, `neq`,
    `lt`, `lte`, `gt`, `gte`) take another tuple of the same length and return a
    condition. A plain value is bound with the type of the expression at the same position
    of the other row; a position with no type on either side is refused (option A: it
    would be compared as text), and so is `null`.
16. **CTE checks.** `withCte` refuses an empty or repeated name, unknown options, a query
    with preloads, and one with `set` (data-modifying CTEs are deferred). It may follow a
    set operation (a `WITH` belongs to the whole statement).
17. **Named-parameter clashes** across the new clauses are refused by the same
    `joinNamed` check, with the clause named (`union()`, `withCte()`, `windows()`,
    `set()`, `join()`).
18. **`where` on a source root.** The object form of `where` is not offered when the root
    has no schema (a subquery or CTE source): with it, TypeScript took a callback for an
    object and left its bindings untyped. Found by the type tests.

## Deviations from the spec

- **Prepared queries are not compiled eagerly** (decision 14), and the repo does not yet
  use `PreparedQuery.plan` (step 12, parallel; Requests). Until it does, a prepared query
  runs like any query (an L1 cache hit by AST identity).
- **Edits outside the owned paths**, each minimal:
  - `query/builder.ts` (step 08): the methods of decision 1, the fifth type parameter,
    `#next`/`patched` for four more properties, the set-operation guard in `#next`,
    `select` refusing an update, the window checks in `select`, `selectMerge`, `orderBy`,
    `exclude`'s four new clauses, `[AS_SUBQUERY]` refusing an update, `render` of the new
    clauses, `RootWhere` (decision 18). Step 08 asked for the property and `exclude` changes.
  - `query/bindings.ts` (step 08): `NullableBinding` uses a binding's own `"~nullable"`
    form when it has one (a source binding's columns become nullable).
  - `query/functions.ts` (step 07): the `over(name)` overload returns
    `Aggregate<T, P> & UsesWindow<N>` (type only); `UsesWindow` added.
    `query/expr.test-d.ts`: one expectation updated for it.
  - `compiler/plan.ts` (step 10): a binding over a subquery or CTE that returns an object of
    values keeps that output (`columns`), and a query with no select over such a root
    returns those objects (decision 11): about 40 lines.
  - `compiler/dialect.ts` (step 10): the eleven window functions in the Postgres
    aggregate table, as step 10 asked.
  - `src/index.ts`, `src/index.test.ts`: the exports above.
  - `docs/site/examples/queries-advanced.ts` (new), as steps 04–10 did for their pages.
- **Snapshots as case tables**, as step 10 did: expected SQL in `advanced-cases.ts`, so
  that step 17 can add dialects and the itest reuses the queries.
- The recursive-tree integration test creates its own `categories` table (the blog
  fixture has none; `test/support` is not this step's).
- No check was disabled, exempted or worked around. No dependency was added.

## Known gaps

- **`outerRef` does not check the outer binding's schema**: `outerRef("u", User)` inside a
  query whose outer `u` is a `Post` compiles to a column of the wrong table (the database
  may refuse it, or not). A column of a binding no query has is refused by the compiler.
- **Window names nested in expressions** (`rank().over("w").add(1)`) are checked only at
  run time; the type mark is on the top expression. In a `QueryWith` scope any name type-
  checks (`W` is `string`), and the run-time check still applies.
- **A window function in `where`, `having` or `groupBy`** is not refused when built;
  Postgres refuses it.
- **`selectedAs("name")` references** are not checked against the select; Postgres
  refuses an unknown name.
- **Tuples** cannot be used with `in` or selected.
- **MySQL and SQLite**: no expected output yet (step 17).
