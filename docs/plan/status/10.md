## Decisions

Each is covered by tests. The ones marked **(sign-off)** change or add to what a user sees
and are also in the table below.

1. **The dialect object is `SqlDialect`.** The contract already uses `Dialect` for the
   name (`"postgres" | "mysql" | "sqlite"`); the table carries it as `name`.
2. **One `Compiler` per adapter instance**, made with `createCompiler(dialect, {
   planCacheSize, codecs })`. `codecs` is the adapter (its `typeOverrides`), so a slot's
   `toDb` is `resolveCodec(type, adapter).toDb`, `undefined` when it is `IDENTITY`. The
   class is internal; the adapter of step 11 delegates its six `compile*` methods to it.
3. **SQL is lower case**, as in the contract's examples and the spike.
4. **Output aliases.** A statement's columns are `c0`, `c1`, … in select order (a
   `selectedAs` item keeps its name; two items with one name are a `QueryError`). A query
   read as a **source** (a subquery in `from` or a join, a CTE body) names its columns so
   the outer query can refer to them: a whole row by its column names, a top-level object
   by its keys, anything else `c<position>`. An outer binding over such a source reads
   `"s"."<that name>"`, and a whole row over it reads the inner row leaf's aliases.
5. **(decided by the owner, 2026-10-15: option A) A value with no type context is cast to
   its type, and must have one unless it is text.** Where nothing in SQL gives a
   placeholder a type (a bare parameter in the select or `RETURNING` list, the results and
   `ELSE` of a `CASE` there, a `coalesce` of nothing but untyped values there, a cell of a
   values list), a typed parameter is cast to its type (`cast($1 as integer)`). An untyped
   one is allowed only for a string or `null`, cast to `text`. Any other untyped value is
   refused with a `QueryError` that names the place and the value's kind and suggests
   `val(value, t.<type>())`, never quoting the value.
   - **Run time.** The compiler checks the value when it makes the plan. A plan is shared
     by every query of the shape, so a text-only slot's `toDb` refuses a non-string value
     on every execution (built once with the plan; `bindParams` already skips `toDb` for
     `null`, and no other slot pays anything, review round 2).
   - **Compile time.** `val(5)`, `val(true)` and `caseWhen(c, 1)` in a `select` or
     `selectMerge` do not compile. `val()` without a type and of a non-text value carries
     a type-only `Untyped` mark, and so does a `CASE` built from such a value; `select`
     refuses a result with a marked leaf at any depth. Since review round 2, `val("x")`
     and a `CASE` started with a plain value carry `NoType` ("no type yet"), so
     `caseWhen(c, "x").else(5)` is `Untyped`, and a `coalesce` none of whose arguments has
     a type is `NoType` or `Untyped` the same way.
   - **Applied to comparisons (review round 2, an application of option A).** Two bound
     values compared (`=`, `<>`, `<`, `<=`, `>`, `>=`, `between`, `like`, `not like`,
     `ilike`, `is distinct from`, `in` a list) have no type in the SQL, and Postgres
     compares two placeholders as text: `val(10).gt(9)` was `$1 > $2`, false, and in a
     `where` it filtered every row out. Now:
     - when either side is typed in the AST, the typed values are cast
       (`cast($1 as integer) > $2`, and the other placeholder takes that type);
     - when neither is, only text may be compared (cast to text), and anything else is a
       `QueryError`, at run time as above and at compile time: `val(10).gt(9)`,
       `val(5).in([1, 2])`, `val(5).between(1, 9)` and `val(5).isDistinctFrom(null)` do
       not compile (a `Comparable` check on the comparison methods).

     The same holds for bound values nested in a `CASE` or a `coalesce` in a select (round
     2, finding 1): a typed argument is cast, so `coalesce(caseWhen(lit(true), val(1,
     t.integer())), 2)` comes back as the number 1, which it did not.
   - **Unchanged.** A typed parameter used as a fragment argument is cast
     (`generate_series($1, $2)` is ambiguous otherwise). An untyped fragment argument is
     left bare, as is an untyped value compared with a column (the column types it).
   - Before the decision, an untyped number came back as the string `"5"` while typed
     `5` (review round 1, finding 6).
6. **Precedence.** Pure precedence would allow `a = b is null`; I chose readable SQL
   that is still correct: an operand of a comparison, `IS`, `LIKE`/`IN`/`BETWEEN` is
   parenthesised unless it binds at least like `||`; an `and` inside an `or` is
   parenthesised (`(a and b) or c`); `not` parenthesises anything but an atom; unary minus
   parenthesises anything but an atom, so `-(-1)` never becomes the comment `--1`; a
   negative literal binds like a unary minus. A fragment binds weakest of all and is
   parenthesised whenever it is an operand (its text is unknown).
7. **`in` on Postgres** is `x = any($1)`, and `notIn` is `x <> all($1)` (the same
   null semantics as `NOT IN`). On a dialect that expands lists, an empty list (only
   possible in a hand-built AST; the builder makes `in([])` the literal `false`) is
   `false` / `true`, and its subject's values are skipped. `in` with a subquery is
   `in (select …)`; with an array expression `= any(expr)` (needs `arrays`).
8. **`exists(q)` with no select of its own selects `1`**, instead of every column.
9. **(sign-off) Set operations.** Every branch is parenthesised. Combinations apply left to right, so
   an `intersect` after a `union` or `except` groups what precedes it
   (`(a union b) intersect c`), since `INTERSECT` binds tighter in SQL. The query's own
   `orderBy` sorts the combined rows, so each order item must be one of the selected
   expressions (or a `selectedAs` name) and is written as its output alias; anything else
   is a `QueryError`. An order item is matched **by structure only**, never by its
   values: the plan is shared by every query of the shape, so the alias it chooses must
   not depend on values (review round 1, finding 1). An order item that matches two or
   more selected expressions (`{ a: age + 1, b: age + 2 }` ordered by `age + 2`) is a
   `QueryError` asking for `selectedAs(…)`. A lock on a set operation is refused.
10. **`updateAll` / `deleteAll`.** Joins become the `FROM` (`UPDATE`) or `USING`
    (`DELETE`) list, with their conditions ANDed into `WHERE`; only `join` and `crossJoin`
    are accepted. `distinct`, `groupBy`, `having`, `orderBy`, `limit`, `offset`, `lock`,
    set operations, windows and hints are refused, naming the clause. `updateAll` needs
    assignments; `deleteAll` and `all` refuse them. `SET` columns are unqualified;
    `RETURNING` uses the select list.
11. **Row-level writes** have no table alias and unqualified columns. Their output plan is
    an `object` keyed by **field name**, each a `value` leaf `c0`, `c1`, … with the field's
    type: step 13 reads it to fill the row. `compileUpdate` needs a non-empty `set` and
    `where`, `compileDelete` a non-empty `where`. A multi-row insert with no columns names
    the first persisted column and gives it `default` in each row (Postgres has no
    multi-row `DEFAULT VALUES`).
12. **(sign-off) `onConflict`.** `"all"` updates every inserted column (target columns included); a
    list updates those fields; `{ except }` the inserted columns minus those. An update
    that is left with no column is a `QueryError` (it would be a syntax error; `"nothing"`
    is the explicit form). On Postgres an update **needs a target**: none given is a
    `QueryError` naming the three forms, rather than an inferred primary key. A fragment
    target is written as it is, after `on conflict`, so it carries its own parentheses.
13. **The plan cache.** L1: a `WeakMap` from the AST object to its plans, one per
    (operation, database schema). L2: an LRU (default 1,000, `planCacheSize`) keyed by the
    shape mixed with the operation, the database schema and, on dialects without array
    parameters, the list lengths; a hit is confirmed by the stored operation, schema,
    lengths and `sameShape`, which compares parameter **types** and schema **metadata** by
    identity (the hash sees only their names). Any mismatch behind an equal key is a
    collision. An L2 hit is remembered at L1 for the new AST. Row-level writes have their
    own LRU of the same size, keyed by a string (schema id, operation, database schema,
    field positions, row count or cell kinds, options); AST parts of the description
    (expression cells, a query source, a fragment target) are compared structurally on a
    hit. Field lists are checked against the schema on every call, hit or miss, since the
    key holds field positions. An explain plan is derived from the query's cached plan and
    cached per (plan, options); a fragment statement is cached by identity and by shape.
14. **Batch inserts:** a plan per exact row count, and `insertChunks(rows, columns,
    maxParams)` splits a large insert into power-of-two chunks, largest first, none over
    the parameter limit. One column list then has at most 17 insert plans on Postgres.
    Step 13 calls it; measuring it is step 19's.
15. **`bindParams`.** A named value that is absent or `undefined` is missing; the error
    lists every missing name once. A named value the plan does not use is an error listing
    the extras and the names it takes. `null` is passed without calling `toDb`. Named
    values are read as own properties only.
16. **`toSql(plan, params, named)`** returns the SQL and the parameters exactly as sent,
    redacted values included: it is a debugging tool, and the guide page says so.
17. **Hand-built ASTs are checked**: `compile` throws when `params` does not hold as many
    values as the tree's parameter nodes. Literals are re-checked (finite numbers,
    booleans, `null`), `fragment.ident` names and window names are re-checked against the
    identifier pattern, a fragment's strings against its arguments.
18. **(sign-off) Unknown function and aggregate names are refused**, not passed through after an
    identifier check: every name must be in the dialect's table. Step 09 adds its window
    functions to the tables (Requests).
19. **A placeholder stays one token in a fragment**: a space is added between `$1` and a
    following digit or word character, and between a preceding word character or `$` and
    `$1` (`$10`, `a$1` and `$$1` would mean something else).
20. **Explain** is `explain (analyze, format json) …`; options the dialect table does not
    list are refused. It runs the query's own plan text with the same slots.
21. **Database-schema provenance follows the contract**: one resolve function where a table
    source is bound; a leaf over a subquery or CTE copies the inner leaf; a set operation
    keeps a schema only when its branches agree; a CTE with a fragment body, a values list
    and a fragment source have none (the leaf takes `meta.schema`). A recursive CTE's
    self-reference reads the rows of the body's first branch, so it adds nothing.
    `CompiledQuery.schema` is the root (or target) table's resolved schema, `undefined`
    when the root is not a table.
22. **The extension registry** (`registerNodeEmitter(kind, { precedence, emit,
    sameShape })`) refuses built-in and already registered kinds. A registered kind must
    also be known to `collectParams` and `shapeOf` (step 07's), which the registry cannot
    do for it.
23. **(sign-off) A query nested in a row-level write takes the write's `schema` argument**
    (review round 1, finding 3): the query of `INSERT … SELECT`, a subquery in an
    expression cell, a subquery in a fragment conflict target. It is the same rule a query
    applies to its own subqueries and joins: the argument is the weakest position, so a
    table of the nested query that has a database schema of its own (its source's, its
    schema class's, or its query's `.schema(…)`) keeps it, and one without reads from the
    write's. Before the fix, `INSERT … SELECT` inherited it and the other two forms did
    not. The argument is the write's `schema` parameter as passed (the per-call option,
    the row's or the repo default), not the target table's resolved schema: a target
    schema class's declared schema applies to the target only, as on reads.
24. **List lengths are part of every plan key where lists are expanded** (review round 1,
    finding 2): besides queries and explains (which had them), the write-plan key of an
    insert whose query source, expression cells or fragment target hold lists, and the
    key of a fragment statement with a list inside it. Without them a cached
    `in (?, ?)` plan was reused for a three-element list, dropping a value.
25. **(sign-off) Where an adapter's compiler takes its dialect from** (after step 11
    merged).
    - **Capabilities** (what the database supports) come from the adapter definition,
      that is from the dialect package (`POSTGRES_CAPABILITIES` of `@egon-orm/postgres`).
      They are the single source: `createStatementCompiler` (`adapter/compiler.ts`) gives
      the compiler the adapter's capabilities and nothing else.
    - **SQL syntax** (quoting, placeholders, the SQL of operators, functions, lock clauses
      and types) comes from the compiler's table for the adapter's dialect name, since SQL
      text is written only from the compiler's tables (ADR 0003, rule 1).
    - The `POSTGRES_CAPABILITIES` in `compiler/dialect.ts` only serves a compiler made
      without an adapter (this step's tests).
    - The two halves are checked against each other when the adapter is created: every
      lock clause the capabilities accept must be one the table can write, and the
      definition's `quoteIdentifier` must quote as the table does; otherwise a
      `TypeError`.
    - The emitter now also checks a lock string against `capabilities.lockModes`, as the
      contract says ("the lock clauses `lock()` accepts as plain strings").
    - **Fix to step 11's package.** `@egon-orm/postgres` listed only the four bare lock
      modes, so `lock("update", { skipLocked: true })` would have been refused. It now
      lists all twelve clauses the builder writes, as step 08 asked.
    - **Rejected alternative.** The package could import the compiler's capabilities, but
      that needs a public export of dialect tables from `egon-orm`, a new public API.
    - **Driver conversions.** The adapter itself is passed as the compiler's codec source
      (`codecs: this`, its `typeOverrides` built from `DriverCodecs`), so slots carry the
      adapter's `toDb`, and `resolveCodec` caches per adapter instance as step 12's
      decoder will.
    - A dialect with no compiler table yet (MySQL, SQLite until step 17) keeps step 11's
      behaviour: its `compile*` methods throw `QueryError`.
    - **A dialect that ignores locks** (`ignoresLocks`, SQLite) writes nothing for any of
      the twelve clauses `lock()` produces (`LOCK_CLAUSES`, `compiler/dialect.ts`),
      whatever its `capabilities.lockModes` lists (an empty list included), and still
      refuses any other lock string (review round 3, finding 1). A lock fragment is not
      written there either.

## Deviations from the spec

- **"SQL snapshots (inline)"**: the expected SQL and parameters are written out in case
  tables (`sql-cases.ts`) instead of Vitest inline snapshots. An inline snapshot is tied
  to one call site, so it cannot be "parameterised by dialect so step 17 only adds expected
  output", and the execution test needs the same statements. Each case has an explicit
  `postgres: { sql, params }`; step 17 adds `mysql` and `sqlite` next to it. I reviewed
  every expected statement by hand before writing it in, and each one runs on Postgres.
- **`repo.toSql` and the cache statistics** are delivered as their parts: `toSql(plan,
  params, named)` and `Compiler.stats()`. The repo is step 12's; the adapter (step 11)
  owns the compiler instance. Requests below.
- **`onConflict` folding**: the spec mentions folding the contract's separate
  `conflictTarget` member into `onConflict` as "a contract change to record". The merged
  contract already has `OnConflict = "nothing" | { target, update }` with no separate
  member, so nothing changed.

## Known gaps

- **Untyped values the types do not catch** (decision 5): the compile-time marks cover
  `val()`, `caseWhen` / `when` / `else`, `coalesce` and the comparison methods. An
  untyped value reached any other way (a hand-built tree, an expression widened to a
  plain `Expr`) is still refused by the compiler with a `QueryError`. Arithmetic on two
  untyped values (`val(5).add(1)`) is not a place the compiler checks; Postgres refuses it
  with "operator is not unique: unknown + unknown" (the reviewer verified this).

- **`val()` infers literal types (predates this PR, step 07):** `val<const T>` types
  `val("b")` as `Expr<"b">` and `val(5)` as `Expr<5>`, so `val("b").gt("a")` and
  `val(5).eq(u.age)` do not compile ("a" is not "b"; `number | null` is not `5`). The
  tests here widen the value first (`const b: string = "b"`). Not changed in this PR: it
  is out of this step's scope (it predates this PR). Request to steps 07 and 09.

- **MySQL and SQLite** are exercised only through fake dialect tables in unit tests
  (positional placeholders, expanded lists, missing capabilities, the clause variants). No
  `?` statement has been executed. Their tables, and three things the table cannot express
  yet, are step 17's (Requests).
- **`contains`, `containedBy`, `overlaps`** need `arrays` or `jsonb`; the emitter cannot
  tell an array operand from a JSON one, so a dialect with only one of them is not refused
  for the other.
- **A bare list selected** (a hand-built `ListNode` in a select list) is written `$1`
  without a cast, since a list has no array type to cast to.
- **Selecting a whole binding over a subquery** needs the subquery to select whole rows of
  that schema; an object select whose keys happen to be the field names is not matched.
- **The zero-collision acceptance** is asserted per shared cache, not by a suite-wide hook
  (see Acceptance).
- **Postgres 14** was not tested; everything ran on the Compose Postgres 16.
- Lateral joins, values sources, table-valued fragments, index hints and data-modifying
  CTEs are future work in README §11; the compiler emits them because the AST has them.

## Follow-up PR: compiler casts

Branch `step/10-compiler-casts`, 2026-10-19. The three fixes the owner approved on
2026-10-19 (status notes 09 and 13, Requests). Option A is unchanged: only a string or
`null` may be left untyped where nothing gives a bound value a SQL type; a column on the
other side of a comparison now counts as that type context. Nothing else is inferred.

### What changed

1. **Typed values in arithmetic are cast** (`compiler/emit.ts`, `binary` and `unary`).
   `+ - * / %` with bound values on both sides follow the comparison rule of decision 5:
   each typed value is cast to its type (`cast($1 as integer) + cast($2 as integer)`),
   which also types an untyped one beside it; with no typed side the arithmetic is refused
   with a `QueryError` when the plan is made, text included (review round 1). Unary minus
   of a bound value is treated the same way (`-cast($1 as integer)`; `-$1` is 42725 too).
   Since review round 1 a typed value beside any operand other than a column is cast too
   (`cast($1 as double precision) / (…)`); beside a column it is left to the column,
   `"p"."views" + $1`. A `CASE` or
   `coalesce` of bound values beside a typed operand in arithmetic has its typed values
   cast (`"u"."age" + case when … then cast($1 as integer) … end`). This applies in
   `where`, `select`, `set` and insert cells, which all write expressions through `binary`.
   `concat` is left as it is: Postgres takes `$1 || $2` as text.
2. **A column compared with a `CASE` or `coalesce` of bound values gives it its type.** For
   `eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `like`, `ilike`, `isDistinctFrom` and
   `between` (on either side), a `CASE` or `coalesce` made only of bound values and `NULL`s:
   - with a typed value in it, the typed values are cast (they type the rest);
   - with none, beside a column of a schema's field, it is cast to that column's type
     (`"p"."author_id" = cast(case when … end as bigint)`), as `set` does (step 09,
     decision 13);
   - `in` / `notIn` an array expression: cast to an array of the subject column's type
     (`= any(cast(coalesce($1, $2) as bigint[]))`), or a `CASE` subject to the element type
     of an array column;
   - otherwise (an operand that is not a column, a column of a source with no schema) it
     is written as before.

   The column's type comes from the binding's schema metadata (`columnType`), which the
   plan's structural check already compares by identity, so the decision is made once when
   the plan is made and is cached with it; nothing runs per call.
3. **`val` infers the widened type** (`query/functions.ts`, step 07's file, approved for
   this PR). The untyped overload is `val<T>(value: T)` instead of `val<const T>`: `val(5)`
   is `Expr<number> & Untyped`, `val("b")` is `Expr<string> & NoType`, so `val("b").gt("a")`
   and `val(5).eq(u.age)` compile. No `const` was needed for enums: next to an enum column
   TypeScript infers the literal from the expected type, so `u.role.eq(val("admin"))`
   compiles and `u.role.eq(val("guest"))` does not (type test).

Also: the write conformance suite's `fragment\`${1}::integer\`` workaround and its comment
are gone (`val(1, t.integer())`); `untyped.test.ts`'s test that pinned the old SQL of a
`CASE` compared with a column now expects the cast; `internals/compiler.md` and
`guide/query-expressions.md` ("Explicit values and types") describe the rules.

### What changed

As it stands after review round 1 (below):

- **The result type widens** (`query/widen.ts`, new; `query/expr.ts`, step 07's file,
  `arithmetic()`; owner row below). Arithmetic of two operands with types in the widening
  order **integer < bigint < decimal < float** is read as the wider operand's type, the
  field type itself (so `bigint({ mode: "number" })` keeps its mode):
  `p.views.div(val(2, t.float()))` is read as a float, `p.views.add(p.authorId)` as the
  bigint. A plain value takes the left operand's type, as before, so the result keeps it.
  Not widened, keeping the left operand's type as before: `mod` (see below) and any type
  outside the order (a custom type made with `defineType`, an untyped operand). The order
  is the one Postgres and MySQL compute in (`numeric` with `double precision` gives
  `double precision`). It is decided when the expression is built (a lookup in a frozen
  table), and the output plan made from it is cached with the plan; nothing runs per call.
- **A typed value beside a column of another numeric type is cast** (`compiler/emit.ts`,
  `typedArithmeticValue` and the new `castBesideColumn`), so the database computes in the
  type the result is read as. In `+ - * /`, a typed bound value (a `param` or `namedParam`
  with a type) beside a column is cast to its own type when both types are in the order
  and their names differ in the dialect: `x.i.div(val(2, t.float()))` is `"x"."i" /
  cast($1 as double precision)` on Postgres, `` `x`.`i` / cast(? as double) `` on MySQL
  and `"x"."i" / cast(? as real)` on SQLite. Either side: `val(6, t.float()).div(p.views)`
  is `cast($1 as double precision) / "p"."views"`.
  - The names compared are the dialect's (`dialect.types`): a `bigint` column beside an
    `integer` value is cast on Postgres (`cast($1 as integer)`, an `int8` result, read as
    the bigint) and not on MySQL (both `signed`) or SQLite (both `integer`).
  - Beside a column whose type is not known (a `values` source, a `subquery` / `cte` that
    selects values, a column node whose column is not its field's) a numeric value is
    cast too: a redundant cast is harmless, a missing one divides as integers.
  - Left to the column, as before: a value of the column's own type (`"p"."views" + $1`),
    a value or column of a type outside the order (a custom type), and `%`.
  - Beside any other operand a typed value was already cast (the earlier PR); unchanged.
- The cast decision is made while the plan is emitted, from the binding's schema metadata
  (`columnType`, as the comparison rule of the earlier PR), so it is cached with the plan;
  a unit test reuses the plan with another value.

### Decisions

1. **Comparisons are not cast** (probed on all three databases; the reviewer agreed).
   Beside a column a value is read as the column's type. Results of the probe (an integer
   column holding 5):

   | Query | Postgres | MySQL | SQLite |
   |---|---|---|---|
   | `x.i.div(val(2, t.float()))`, before | 2 (silent) | 2.5 (decimal `"2.5000"`) | 2.5 |
   | `x.i.mul(val(0.5, t.float()))`, before | 22P02 | 2.5 | 2.5 |
   | `x.i.lt(val(5.5, t.float()))` | 22P02 | correct | correct |
   | `x.i.eq(val(5, t.float()))` | correct | correct | correct |
   | hand-written `i / cast(? as <float>)`, `i < cast(? as <float>)` | 2.5, true | 2.5, 1 | 2.5, 1 |

   Only Postgres goes wrong in a comparison, and loudly (22P02). Casting there would break
   comparisons that work today, because the column's type is what parses the value: a
   `date`, `uuid` or `numeric` column compared with a value typed `t.string()` would become
   `date = text` / `uuid = text`, which Postgres refuses (42883, probed). The guide gives
   two workarounds: cast the column (`p.views.cast(t.float()).lt(val(7.5, t.float()))`,
   which keeps an index on it from being used), or compare with the integer meant
   (`p.views.lt(val(8, t.integer()))`). A Postgres test runs the first and pins the 22P02
   of the uncast form.
2. **`%` is neither widened nor cast beside a column.** Postgres has no `%` for
   `double precision` (`integer % double precision` does not exist), so casting would turn
   `x.i.mod(val(2, t.float()))`, which runs today, into an error. It keeps the left
   operand's type and the value is left to the column, as before.
3. **A custom type has no place in the order** (owner: keep today's behaviour). A custom
   value beside a column, or a typed value beside a custom column, is left bare and the
   result keeps the left operand's type. This is also what keeps MySQL working (review
   finding 2): its `CAST` takes few type names, and `cast(? as numeric(10, 2))` is a parse
   error (1064). The reviewer asked for a dialect-table flag that leaves custom values
   uncast on MySQL; with custom types never cast beside a column on any dialect, such a
   flag would have nothing to switch, so none was added (decision recorded for the
   reviewer). The older paths that do cast a custom value on MySQL (two bound values, a
   value in a select list or a fragment) are unchanged; Known gaps and Requests.
4. **Type names, not `DbType` kinds, are compared** for the cast, so "the same type" is
   what the dialect would write in a cast (MySQL `signed` for integer and bigint, SQLite
   `integer`). The widening itself compares kinds (it decides the decoder, which is the
   same on every database).
