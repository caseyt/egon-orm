## Decisions

**Approved by the owner on 2026-10-18, all 16 decisions, after PR #23 merged.**

Recorded for the owner's sign-off. Where there was an open choice I took the explicit
option.

1. **`createAdapter` is public.** A dialect package reaches core only through `egon-orm`
   (there is no `egon-orm/adapter` entry, and `dist/internal.js` is not published), so
   the factory must be exported. The driver-wrapper interfaces stay unnamed (spec):
   `@egon-orm/postgres` derives them from `Parameters<typeof createAdapter>`. TSDoc says
   applications call `postgres(...)` instead.
2. **Driver fixes per column kind, composed by core.** The spec has the dialect supply
   "type overrides". Writing `Codec`s directly in the dialect package would need
   `IDENTITY` (not public, and `index.test.ts` keeps it so) and would have to dispatch on
   the type (status 03: `bigint` and `bigint(number)` share a kind). Instead a dialect
   declares `DriverCodecs` (`{ bigint: { fromDb }, json: { toDb }, ... }`) and core
   composes each fix with the type's own conversions (`fix` before `fromDb`, `toDb` before
   `fix`; the identity is skipped by reference). Every type of a kind is right, custom
   ones and embeds included.
3. **Postgres values.** Per-statement result parsers (`types` in each query config and
   cursor), not pool-level and never global: `int8`, `numeric`, `date` stay text;
   `timestamp` is read as UTC wall time; `timestamptz` is parsed by us (offsets with
   seconds included), so a global `pg.types` change elsewhere in the process does not
   affect these kinds. Driver fixes: `int8` text to `bigint` (also the `numeric` of
   `sum(bigint)`); `Buffer` to a plain `Uint8Array` view; JSON serialised by us;
   `Date`s written as UTC text (`...+00` for `timestamptz`), independent of the process's
   zone (`pg` writes the local offset in hours and minutes, which loses the seconds of
   historic offsets such as year 1). `bigint(number)` gets `BigInt` then its own check.
4. **`ping()`, `poolStats()` and parameter opt-in live on `DatabaseAdapter`**, not on the
   contract (as the carried-over note asked). Parameters reach a `query` listener only if
   it subscribed with `{ params: true }`; others get `params: undefined`. This is how
   step 12's `log: { params: true }` maps onto the adapter, with no adapter option.
5. **A throwing listener** does not fail the statement or stop other listeners; its error
   is rethrown on a microtask, so it surfaces as an uncaught exception instead of being
   swallowed (packages may not log). **Consequence: by Node's default, an uncaught
   exception ends the process, so a listener that throws takes the application down**
   unless it handles `uncaughtException`. The guide says so and tells users to catch
   errors in their listeners. The alternative is to swallow the error silently; this is
   the owner's call (sign-off table).
6. **Cancellation** (changed in rounds 1, 2 and 3). `signal` / `timeoutMs` send the
   protocol's cancel request (`packages/postgres/src/cancel.ts`), what libpq's
   `PQcancel` sends: a new socket carrying the backend's process id and secret key (from
   `pg`'s connection), closed by the server once handled. It needs no login and no free
   connection slot, and PgBouncer forwards it (with `pg_cancel_backend`, used before
   round 1, a pooler's fake process id made it useless, it needed an authenticated
   connection and a free slot, its result was ignored and its connect had no timeout).
   - **Where it goes** (round 2): the remote address and port of the connection's own
     socket, as libpq does, so DNS round-robin, several poolers or a load balancer cannot
     route it to another server; the configured host and port only when the socket has no
     remote address (a Unix socket).
   - **TLS** (round 2): when the connection uses TLS (`client.ssl`, set by `ssl` or by
     `sslmode` / `ssl` in the connection string), the cancel socket sends an SSLRequest
     and runs the TLS handshake with the same options `pg` uses (its `ssl` options,
     including a client certificate's `key`, which `pg` makes non-enumerable and copies
     explicitly (round 3); the certificate checked against the configured host name, SNI
     unless that is an IP);
     with `sslNegotiation: "direct"` it starts TLS at once with the `postgresql` ALPN
     protocol. If the server refuses TLS or the handshake fails, the request is not sent:
     never in plain text when `ssl` is set. Without `ssl`, it is sent in plain text, like
     the connection itself.
   - **A failed cancel request** (round 2): the bytes may have gone out and could reach
     the server late, so the connection is never reused. A pooled connection is closed on
     release; a dedicated one refuses further statements with `DatabaseError`
     (`"connection"`) and is closed on release. The statement itself runs to its end, and
     only then does the call reject.
   - **Limits, stated plainly:** the server never says whether a statement was stopped;
     delivery is bounded by the pool's `connectionTimeoutMs`, 10 s without one; poolers
     other than PgBouncer (RDS Proxy, Supavisor) were not tested and may not forward
     cancel requests.
   - The call rejects only after the statement has ended **and** the cancel request was
     delivered (or failed), so a late cancel cannot hit the next statement on a reused
     connection. It rejects even if the statement completed anyway (`cause` undefined);
     otherwise `cause` is the driver's error. A signal that has fired runs nothing.
     `timeoutMs` is one budget for the whole call (round 1): the wait for a connection
     counts, a call that waits longer rejects with `"timeout"` without running, and the
     statement gets what is left; an abort while waiting stops the wait too (the late
     connection goes straight back). Both together: one cancel request, the first reason
     wins.
7. **Streams.** `pg-cursor` is an optional peer loaded on the first stream; missing, it
   is a `QueryError` saying how to install it. Default `batchSize` 100. `timeoutMs`
   bounds the wait for a connection and then each round trip of a stream. While a stream
   is open on a dedicated connection, another statement or stream on it is refused with
   `QueryError` (round 1): it would queue behind the cursor, and `release()` would wait for
   it forever. An abort between reads closes the cursor and keeps the connection; only a
   read that was in flight (and so was cancelled) closes it. One `query` event per stream, when it ends,
   with the total row count and the time from opening to the end (consumer time
   included). A cursor read that fails or is cancelled, or a cursor that cannot be closed,
   closes the connection instead of reusing it; so does releasing a dedicated connection
   with a stream still open. A stream whose dedicated connection was released or
   destroyed stops at its next fetch with `DatabaseError` (`"connection"`) and does not
   try to close its cursor on the ended connection (round 2).
8. **Connections that are not reused:** a fatal error (normalised code `"connection"`),
   a connection still inside a transaction when it is returned (dedicated or pooled, as
   reported by `pg`'s transaction status), a connection whose cancel request failed
   (decision 6), a checked-out connection whose client reported an error between
   statements (round 1), and the cases of decision 7.
9. **A pool you bring** is used as it is: no listeners besides `connect` / `remove`, no
   `error` listener (that is the owner's), its type parsers untouched (decision 3 makes
   that unnecessary), and `close()` does not end it. Connection options together with it
   are a `TypeError`. The cancel request for one of its connections works as in
   decision 6: it goes to the address that connection's socket is connected to, uses TLS
   when the connection does (with the pool's TLS options as `pg` resolved them), and is
   bounded by the pool's `connectionTimeoutMillis`. The guide tells users to add their
   own `pool.on("error")` listener (round 1).
10. **Error mapping.** As specified, plus: `57014` (statement timeout, or a cancel from
    another session) is `"timeout"`; class `08`, class `28` (authentication), `57P01`
    (also `pg_terminate_backend`), `57P02`, `57P03`, `53300`, Node network codes and
    `pg`'s own connection messages are `"connection"`; anything else with a SQLSTATE is
    `"database"`. Our message repeats the database's only for classes whose messages
    never quote a value (`42`, `40`, `25`, ...); for the others (data exceptions above all)
    it points to `error.cause`. Errors that are not `pg`'s are returned unchanged.
11. **Options.** Unknown keys and wrong types throw `TypeError` when `postgres()` is
    called (JavaScript callers and typos); `undefined` counts as left out, so
    `connectionString: process.env.DATABASE_URL` compiles under
    `exactOptionalPropertyTypes` (found by the type-checked guide example). `pool`
    defaults to `{ max: 10 }`; other pool settings default to `pg`'s.
12. **`begin(options)`** writes Postgres's syntax (`begin isolation level serializable,
    read only, deferrable`, and `read write` / `not deferrable` for `false`) from a table;
    an isolation level missing from `capabilities.isolationLevels` is a `QueryError`,
    wrong types are a `TypeError`. Savepoint names must be non-empty strings without NUL.
13. **Misuse after close or release** is a `DatabaseError` with the code `"connection"`.
14. **A statement list without parameters** returns the last statement's result (`pg`
    reports one per statement).
15. **Capabilities** are all true, as specified, including `lateralJoin` (lateral joins
    are future work in the builder; the flag only says Postgres can do them);
    `maxParams` 65,535.
16. **`poolExhausted`** fires when a checkout has to wait (no idle connection and the pool
    at `max`); the pool is asked only when someone listens.

## Deviations from the spec

- **`compile*`** do not work yet (Acceptance, first box): the compiler is step 10's,
  which is not merged.
- **The leak check is per test file, not a global teardown** (Acceptance, last box).
- **`DriverConnection` has `cursor`, `cancel` and `inTransaction`** besides `query`
  (the spec lists `query` and `stream`): the shared adapter needs the cancel request and
  the transaction state, and owns the stream loop itself (batches, early exit, abort).
  `DriverWrapper` also has `stats` and `saturated`.
- **The dialect gives `DriverCodecs`, not a `typeOverrides` function** (decision 2). The
  adapter's `typeOverrides` is still the contract's function.
- **`ConstraintError.sql`** was added in `packages/core/src/errors.ts` (not owned by this
  step): the spec says to attach the SQL to normalised errors and the guide's errors page
  says errors contain it, but only `DatabaseError` had a field for it. An optional
  constructor detail and a read-only member; nothing else changed. One test added in
  `errors.test.ts`.
- **`docs/site/package.json`, `docs/site/tsconfig.json`** gained `@egon-orm/postgres`,
  `pg` and `@types/pg` and a project reference, so that the guide's Postgres examples are
  type-checked (plan README §8).
- **Driver choice (item 11): `pg` only.** A second wrapper over postgres.js is not worth
  its upkeep now: `pg` is what the Drizzle, Sequelize and Prisma (driver adapter) users
  this library targets already run, postgres.js has its own pool, type handling, cursor
  and cancel semantics (a second set of every decision above), and nothing in the plan
  needs it. Future work, behind the same options, if users ask.

## Review, round 1

The reviewer requested changes (10 findings). All were taken.

1. **A checked-out connection that the server dropped crashed the process.** pg-pool
   listens for client errors only while a client is idle, so a backend ending between
   statements emitted `error` with no listener. Each checkout now listens itself
   (`PgConnection.onError`, removed on release) and marks the connection broken, so it is
   closed on release. The termination test is deterministic: the Postgres profile's
   `terminate` uses `pg_terminate_backend(pid, 5000)`, which returns once the process has
   ended, and the test then waits 100 ms so that the error reaches the idle checked-out
   connection (the case that crashed). Without the listener it fails 3 runs out of 3;
   with it, the Postgres integration project passed 10 out of 10. The "three runs in a
   row" claims were corrected. Unit tests for both listener paths.
2. **`timeoutMs` did not bound the wait for a connection.** It is now one budget for the
   whole call (decision 6): the checkout gives up with `"timeout"` ("waited longer than its
   timeoutMs ... for a free connection"), the late connection goes back to the pool, and
   the statement gets the remaining time. Unit tests (wait, abort while waiting, remaining
   budget) and a conformance test (busy pool, `timeoutMs: 200`, rejected in under 1.5 s).
   Documented in the guide.
3. **`pg_cancel_backend` had undisclosed gaps.** Replaced by the protocol's cancel request
   (`cancel.ts`, the preferred fix), with its limits stated in decision 6 and the guide.
   Unit tests against a loopback server (message bytes, TCP and Unix socket, refused,
   timeout); the conformance cancellation tests exercise it against Postgres 14 and 16.
4. **`release()` hung behind a statement queued after an open stream.** Chose the explicit
   option: a statement or stream on a connection with a stream open throws `QueryError`
   (decision 7). Unit and conformance tests.
5. **An abort between stream reads closed a healthy connection.** The signal is checked
   before each read; only a read in flight marks the connection broken. Unit tests for
   both cases and a conformance test that the same backend serves the next statement.
6. **Decision 5 did not say a throwing listener ends the process.** It does now, with a
   sign-off row and a sentence in the guide. The policy is unchanged.
7. **Conformance cases that do not apply passed silently.** They use `test.for` and the
   context's `skip()` with a reason (round trips, constraint kinds, isolation levels).
8. **A closure per statement on a dedicated connection.** A module-level `ignoreError`
   replaces it (also in the cancel path).
9. **`Telemetry.queryParams` was never read.** Removed.
10. **The guide did not ask for a pool `error` listener.** "Bringing your own pool" now

## Review, round 2

The reviewer confirmed the ten round-1 fixes (integration 8 runs out of 8, no unhandled
errors) and requested changes: 4 findings. All were taken.

1. **A stream on a released connection hung.** `cursorRows` now takes an `open()` check:
   before each fetch, a stream on a dedicated connection that was released or destroyed
   throws `DatabaseError` (`"connection"`), and its cursor is not closed once the
   connection has ended (that answer would never come), so leaving the loop settles at
   once. Unit tests (next fetch, `return()` after release and after destroy) and a
   conformance test; with the check removed, the conformance test times out (30 s).
2. **The cancel request could reach a different server.** It now goes to the connected
   socket's `remoteAddress` / `remotePort`, falling back to the configured host and port
   (Unix sockets); the configured host stays the TLS server name. Unit tests for both.
3. **A failed cancel request left the connection in use.** Such a connection is now never
   reused (a module-level `WeakSet` the check-in consults): pooled, it is closed; dedicated,
   it refuses further statements and is closed on release. Unit tests with a fake driver
   whose `cancel()` rejects, for both; a test that a delivered cancel still reuses the
   connection. Decision 6 updated.
4. **The cancel request went without TLS when `ssl` was set.** Took the better fix: the
   cancel socket negotiates TLS like the connection (SSLRequest, then the TLS handshake
   with the same options; direct TLS with ALPN for `sslNegotiation: "direct"`), and fails
   rather than fall back to plain text (then finding 3 closes the connection). Unit tests
   on loopback servers with a self-signed certificate (`packages/postgres/test/tls-fixture.ts`,
   loopback only): plain text without `ssl`; SSLRequest then TLS; the certificate checked
   against the configured host name (a wrong name fails); an IP host without SNI;
   `ssl: true` refusing a self-signed certificate; an `N` answer refused with nothing sent;
   a server that closes early; direct TLS with the `postgresql` ALPN; invalid TLS options.
   **Real check:** a private `postgres:16-alpine` container with `ssl = on` and a
   `pg_hba.conf` that rejects every non-TLS connection (`hostnossl ... reject`), removed
   afterwards. With `ssl: { ca }` (certificate verified against `localhost`),
   `ssl: { rejectUnauthorized: false }`, and `?ssl=no-verify` in a connection string, a
   `pg_sleep(10)` with `timeoutMs: 300` was cancelled in 308–326 ms; each cancel made
   exactly one TLS handshake (counted by wrapping `tls.connect`), and the same backend
   served the next statement (so the request was delivered, not failed). The guide's
   comparison with `psql` is gone; the sign-off table has the round-2 rows.

## Review, round 3

The reviewer verified the round-2 fixes (integration 8 runs out of 8) and requested one
change, which was taken.

1. **The cancel request dropped a client certificate's private key.** `pg` makes
   `client.ssl.key` non-enumerable (`pg/lib/client.js`, `pg/lib/connection-parameters.js`),
   so `Object.assign` copied the certificate without its key, and a server that requires
   client certificates refused every cancel request. `cancel.ts` now copies `key`
   explicitly when it is present, as `pg/lib/connection.js` does. I checked the rest of
   `pg`'s TLS handling: `key` is the only option it hides or copies by hand (`password`,
   the other non-enumerable field, is not a TLS option); everything else goes through
   `Object.assign` in `pg` too. Two unit tests with a loopback TLS server that requires a
   client certificate (a second self-signed pair, CN `egon-test-client`, in the test-only
   fixture file): with ssl options whose `key` is non-enumerable, the cancel request is
   delivered and the server sees the client certificate; without the key, the server
   refuses it and nothing is sent. With the explicit copy removed, the first test fails
   with `certificate required`.
