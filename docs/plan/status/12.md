## Decisions

Each is covered by tests. **(sign-off)** marks the ones a user sees; they are also in the
table below.

1. **Awaits per call** (corrected in review round 1). `repo.all` is not async: it calls
   `load`, the one async function of the pipeline, which awaits `executor.execute` once
   (the adapter's own awaits are inside that call), plus `afterDecode` for a query with
   preloads. So N = 1 repo-level await for `all`; `one`, `oneOrThrow`, `first`, `get`,
   `getBy`, `count`, `aggregate` and `reload` add one (they await `load` and post-process).
   No closure is made per call (the statement-level reads use module-level finishers).
   With no options and nobody listening, the execution options are one object per plan,
   reused; otherwise one object of a fixed shape per call.
2. **(sign-off) `first` never exceeds the query's own limit** (review rounds 1 and 2).
   Without a limit it adds `LIMIT 1`; with one it uses
   `LIMIT CASE WHEN <own> < 1 THEN <own> ELSE 1 END`, so `limit(0)` (or a limit parameter
   bound to 0) returns nothing, and the offset is kept. The reviewer suggested `least(…)`;
   `least` is not in the compiler's function table (step 10, decision 18), and a `CASE`
   says the same with nodes the compiler already writes. Both uses of the query's limit
   are cast to `bigint` (review round 2): inside a `CASE` Postgres types the limit as a
   32-bit integer, so `first(q.limit(Number.MAX_SAFE_INTEGER))` failed where `all` worked.
   It adds no order.
3. **(sign-off) `exists` and `aggregate` wrap where rewriting would change the answer**
   (review rounds 1 and 2).
   - `exists` is `SELECT 1 … LIMIT 1` without select, order, distinct and preloads, as
     specified, except that the query is wrapped (`SELECT 1 FROM (q) AS "s" LIMIT 1`)
     when it has a limit of its own, a set operation (the branches' selects decide an
     `INTERSECT` / `EXCEPT`), `distinct` (or `DISTINCT ON`) together with an offset, or a
     select that aggregates without a `groupBy` (it has a row even over no rows).
   - `aggregate` wraps a query with a limit, offset, distinct or set operation as
     specified, and also one with a `groupBy`, a `having`, a row lock (Postgres refuses
     `FOR UPDATE` with an aggregate) or a select that aggregates by itself.
   - "Aggregates by itself": an aggregate function that is not a window function (or a
     window function whose arguments aggregate). A fragment, or an expression kind the
     repo does not know, cannot be checked and counts as possibly aggregating (the safe
     side); the `QueryError` of a wrapped field aggregate then says so and suggests
     computing the aggregate in the query's own select. Only expression children are
     walked (review round 2): never parameter values, their types, or subqueries.
   - A wrapped aggregate over a field needs the field's **column** in the inner select:
     whole root rows, or an object whose key of that name is that very column of the
     root binding. A key that only has the name (`{ views: p.id }`, `{ views: count() }`)
     is a `QueryError`.
4. **(sign-off) `aggregate` typing** follows step 07's `sum` / `avg` / `min` / `max`: the
   field must be a column of the root binding; `sum` / `avg` take number, bigint and
   string (decimal) columns; `count` returns `number`. The guide's "`number | null`" is
   now per function.
5. **Telemetry.** The repo listens to the adapter only while it has `query` listeners
   (so an unobserved repo costs the adapter nothing), with `{ params: true }` when
   `log: { params: true }` (step 11's request). Each call hands the adapter a `Call`
   object as `context`; the adapter's event for that statement is matched to it, and the
   repo emits after decoding, adding `operation`, `source` (the root table), `decodeMs`
   and the caller's `context`. Statements other repos run on the same adapter are not
   reported. A listener that throws is treated as the adapter does (decision 5 of step 11,
   approved). A stream reports once, at its end, with the total decoding time. A decoding
   failure is reported as the event's `error`.
6. **(sign-off) `log`.** `true` writes one line per statement to standard error through
   `process.stderr` (packages may not use `console`); a function receives each event;
   `{ params: true }` writes lines with parameters and makes every `query` event of the
   repo carry them. There is no way to get parameters into a custom function without the
   stderr lines (see the owner table).
7. **(sign-off) `operation` values** are the method names; a throwing twin reports its
   base (`oneOrThrow` is `"one"`), `count` is `"aggregate"`.
8. **The alias of a schema read** (`repo.all(User)`) is the table name (`"t"` for a table
   whose name starts with `$`, which aliases may not).
9. **(sign-off) `repo.planCacheStats()`** and `adapter.planCacheStats()` expose the
   compiler's counters (step 10's request). A new public method on both; see Deviations.
10. **(sign-off) Streams need no transaction on Postgres** (step 11's finding): `stream`
    runs on the adapter directly. The guide's sentence about opening a transaction is
    replaced. Default `batchSize` 500 (the spec), the adapter's own default stays 100.
11. **Options are checked.** An unknown option key, a non-object, an empty `schema` or a
    non-object `context` is a `TypeError`; so is passing named parameters to a query that
    has none (they land in the options position and are an unknown option), and a third
    argument where only two fit. `timeoutMs`, `signal` and `batchSize` are checked by the
    adapter, which uses them.
12. **Derived queries and named parameters.** A named parameter used only in a clause a
    derivation drops (an `orderBy` under `count`) is still required by the types and
    checked by name, but not bound.
13. **`get`** builds `from(Schema, table).where({ key: id })`; `null` / `undefined`, an
    object for a single key, a scalar for a composite key, a missing / `null` / extra key
    field, and a keyless schema are `QueryError` before anything runs. `get` takes a
    schema class only (the spec and the guide).
14. **`getBy`** uses the query's `where(object)`, so it needs a builder query or a schema
    class; another `QueryLike` is a `QueryError`.
15. **`reload`** groups rows by (schema, database schema) and reads each group with the
    statements of decision 20, whose table source carries the rows' database schema
    (strongest position, as the adapter contract says); results come back in input
    order, `null` for a gone row; `reloadOrThrow` throws `NoResultsError` with that
    query's rendering.
16. **`explain`** returns the first column of each row joined by newlines (`format`
    text), or the first cell parsed (`json`).
17. **`afterDecode(rows, plan, ctx)`** is the hook step 14 fills; it is called only for a
    plan whose output carries preloads, and for now throws `QueryError` (a preload query
    cannot run yet). `stream` refuses preloads before running anything.
18. **(sign-off) Decoders** (review rounds 1 and 2) are stored on the plan by whichever repo runs it first;
    generated and interpreted ones give the same rows, so another repo with other
    `codegen` reuses it. `codegen: true` falls back silently to the interpreter where
    `new Function` is refused; whether it is allowed is probed once, the first time a
    repo with `codegen` on builds a decoder (review round 1: no longer at module load).
    `codegen` governs the repo's row decoders only: the schema and validator modules still
    probe `new Function` once when they load (Requests, steps 04 and 06), so
    `codegen: false` alone does not keep a strict CSP from seeing an attempt.
19. **`get` refuses an array id unless the key field holds arrays or JSON** (review
    rounds 1 and 3): for any other field the object form of `where` would read the array
    as `IN`, and `get` would return one of several rows. For a field that holds arrays
    or JSON, the array is the value compared.
20. **(sign-off) `reload` statements stay small** (review rounds 1, 2, 4 and 5). The given
    keys are joined to the table as a list that carries each key's 1-based position:
    - on a dialect with array columns and array parameters (Postgres), when no key field
      holds arrays or JSON:
      `join unnest($1, $2) with ordinality as "$keys" ("k0", "k1", "position") on t.key0 = "$keys".k0 and …`,
      one typed array per key field, one statement of fixed size for any number of rows;
      the `unnest … with ordinality` text is constant strings of a fragment source the
      repo builds, chosen by capabilities (not by dialect name);
    - otherwise `join (values (cast($1 as …), cast($2 as …), $3), …) as "$keys" (…)`, at most
      1,000 rows a statement and never more parameters than `capabilities.maxParams`
      (key fields plus the position, per row).

    The list's alias is `$keys` (review round 5): aliases starting with `$` are reserved
    for the library, so it never meets a table's alias, and its columns are always
    qualified by it. Every value is bound. The select is `{ row: <the root row>, position: "$keys".position }`;
    the position places the row and is not a property of it. (Round 1 chunked only by
    `maxParams`; a 32,767-arm `OR` made the reviewer's Postgres backend run out of
    memory.)
21. **(sign-off) The database matches the keys** (review round 4, replacing round 3's
    encoding). `reload` no longer compares keys in JavaScript: each row read back carries
    the position of the given key it matched (decision 20), so a key is found exactly when
    the database's equality says so: a decimal whose scale changed, a custom type
    (whatever its application value holds), bytes, arrays, strings that would run
    together as text. Round 3's `encodeKey` is gone: its `JSON.stringify` fallback made
    every key of a custom type with private state `{}`, so keys 100, 200, 300 reloaded
    as the same row. A key field that holds arrays or JSON goes through the `values` form
    (`unnest` flattens a two-dimensional array). `get` accepts an array id for such a
    field, and refuses one for any other.
    **Remaining limit:** a key value the given row cannot hold exactly. A timestamp key
    with microseconds is read into a millisecond `Date`; bound back, it no longer equals
    the stored value, so `reload` returns `null` for that row (and `get` with that `Date`
    finds nothing). Documented in the `reload` TSDoc, the guide and Known gaps; a
    conformance test pins it.

## Known gaps

1. `reload` of a `Loaded` row: the type keeps its associations; the fresh row has none.
2. Preloads do not run (step 14); `getting-started.md` shows `.preload("posts")`, which
   compiles but throws `QueryError` until then.
3. The read suite seeds through `adapter.execute` with unquoted identifiers and
   `profile.param`, which should port; the Postgres-only parts are in the profile. It was
   run on Postgres 16 only.
4. `exists` and `aggregate` read a wrapped query through a subquery aliased `"s"`. A
   query whose own tables, CTEs or joins use `s` is fine (the subquery is its own
   scope), but the alias shows in the SQL.
5. `reload` (and `get` with a `Date`) cannot find a row whose timestamp key has
   microseconds: the row's `Date` holds milliseconds (decision 21).
6. `reload` casts the keys to their fields' declared types, so a key column whose real
   type differs fails ("operator does not exist: mood = text" for a `t.enum` key on a
   native Postgres enum column), while `where` and `get` work. The remedy is to declare
   the field with `defineType` and the column's SQL type (`db: { kind: "custom", sql:
   "mood" }`), confirmed on Postgres in review round 6 for single and composite keys, in
   both SQL forms (`unnest` and `values`). Documented in the `reload` TSDoc and the guide
   (review round 5).

## Review, round 1

The reviewer requested changes: 12 findings, the first five reproduced on Postgres. All
were taken. The conformance tests for findings 1–4 each fail when their fix is undone
(checked on Postgres by reverting each fix in turn: 4 failures, then restored).

1. **`exists` with `distinct` (or `DISTINCT ON`) and an offset answered wrongly.**
   Wrapped now, and so is a select that aggregates without a `groupBy` (found while
   fixing this: `exists` of `select count(*) … where false` is true). Decision 3, guide,
   unit and conformance tests.
2. **`count` / `aggregate` of a locked query failed** (`count(*) … for update`). A lock
   now wraps, as does a self-aggregating select (`count` of `select count(*)` is 1).
   Conformance tests with `lock("update")` and `lock("share")`.
3. **A wrapped aggregate trusted the key's name.** The key counts only when its value is
   the root binding's column of that field; `{ views: p.id }`, `{ views: count() }`, the
   column of another binding and a missing key are `QueryError`. Unit and conformance
   tests.
4. **`first` overrode a smaller limit.** It now uses `CASE WHEN own < 1 THEN own ELSE 1
   END` (decision 2 says why not `least`). Conformance: limit 0, limit parameter 0 and 3,
   limit 5, limit 5 with an offset, no limit.
5. **`get` turned an array id into `IN`.** Refused unless the key's type is an array
   (decision 19); tests for a scalar key, a composite key part and an array-typed key.
6. **The "one await" claim.** `repo.all` is no longer async and calls `load`, which
   inlines what `run` did; `loadDerived` is folded into `load`; the statement-level reads
   use module-level finishers, so there is no per-call closure. Decision 1 states the
   counts per method.
7. **`new Function` at module load.** The repo's probe is lazy (`generationAllowed()`),
   asked only when a decoder is generated; a test re-imports the module and counts
   `Function` constructions (none with `codegen: false`; probe then decoder with it on).
   The silent fallback is in the owner table and the guide. Other modules still probe at
   load (Requests, steps 04 and 06).
