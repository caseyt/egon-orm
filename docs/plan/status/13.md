## Decisions

1. **Order of insert.** Invalid → failure; then `prepareChanges`; then (if still valid)
   the values and the required-field check; then SQL. The check runs after the prepare
   functions so that one may supply a required value. Prepare functions never run on an
   invalid changeset.
2. **Required fields** (insert): a persisted, non-nullable field that ends up with no value
   or `null`, is not database-generated and is not `writable("never")`, is `can't be blank`
   (`validation: "required"`). An update that sets a non-nullable field to `null` (possible
   with `change`) gets the same error instead of a raw `NOT NULL` violation.
3. **Writable modes.** `"never"`: never written by `insert`/`update` (a change to it is
   dropped silently, as a declared schema rule) and always read back; `insertAll` rows that
   give it a value are refused with `QueryError` (the rows are explicit, dropping would
   lose data). `"insert"`: written on insert, never updated (dropped silently).
4. **What insert reads back**: primary key, `dbGenerated()` and `writable("never")` fields,
   plus `returning`. A nullable field left out is `null` on the returned row even if the
   column has a database default the schema does not declare (`returning` reads it).
5. **An upsert that updates reads the whole row back** (`RETURNING` every column), so the
   returned row is the stored one, not the values sent.
6. **Wrong changeset kind** (loaded row to insert, new record to update/delete): `QueryError`
   at run time, and a compile error when the type is certain (`Changeset<S, false>` /
   `Changeset<S, true>`); `Changeset<S, boolean>` is accepted.
7. **No-op update.** The prepare functions run first (so `optimisticLock` always writes,
   since it forces a change); then no change and no `force` returns the row, no query. A
   change only to virtual fields, or to fields that may not be updated, sends nothing and
   returns the row with the virtual changes. `force` with nothing to set (no `updatedAt`)
   sends nothing either. `updatedAt` is generated only when the update writes.
8. **Stale rows.** `staleError` adds `{ message: message ?? "is stale", validation:
   "stale", meta: { stale: true } }` on its key; `allowStale` returns the row as if written.
   `delete` takes both, and no `returning` (the spec lists none for it).
9. **Constraint errors** carry `constraint: <declared type>` and
   `meta: { constraint, constraintName: <declared name> }`. The first matching declaration
   wins. Unhandled: the message names the type, the name, the action ("insert into",
   "update of", "delete from") and the table, then the call to add: the default form when
   the reported name is a default name of fields of this schema (columns with `_` are split
   by trying every split), always the `{ name }` form, with `"<field>"` /
   `"<association>"` when it cannot be read from the name. For a delete, the association
   is found by the child table and the name. `notNull` and nameless violations are
   rethrown unchanged. The message never quotes a value; `detail` and `cause` are kept.
10. **insertAll values.** Timestamps of one generator get one instant for the whole call;
    other generated values (uuids) one per row. A top-level untyped `val(x)` is bound with
    the column's type (option A: the target column is the type context); a typed
    expression is emitted as it is. A subquery is written `scalar(query)` (typed); a bare
    query as a value is refused with a pointer to `scalar`. `param(name, type)` cells are
    placeholders filled from `placeholders`; a name used and not given, or given and not
    used, is a `QueryError`. `returning: true` gives schema rows; a list gives plain objects
    (`Pick<Row, F>`), not half-filled class instances.
11. **insertAll chunks** come from `insertChunks(rows, columns, maxParams - conflict
    params)` (step 10's request) when every cell is a plain value; otherwise rows are packed
    greedily by their placeholder count. More than one chunk runs in one transaction: on
    the repo's pool, its own (`begin`/`commit`, `rollback` on failure, the connection
    destroyed if the rollback fails); on an executor that is already a connection (step
    16), the statements join that transaction. The wait for that connection counts
    against `timeoutMs`, and the signal stops it; a connection that arrives late is
    returned.
12. **`INSERT … SELECT`**: the select must be an object whose keys are fields and whose
    values are expressions (a plain value in a select is kept out of the SQL, so it is
    refused with a pointer to `val(value, type)`).
13. **`updateAll`** refuses a schema class and a query without `.set(...)` before
    compiling (step 09's request). A `PreparedQuery` given to `updateAll` or `deleteAll`
    uses its own plan (`prepared.plan(adapter, operation, schema)`), as step 09 asked of
    whoever next touches the repo.
14. **`validateUniqueAsync`** queries only when one of the fields changed, all have a value
    and none has an error; excludes the row's own key on update (`not (key = …)`); its error
    is `{ message, validation: "uniqueAsync", meta: { fields } }`, the message may be a
    function of `meta`. The implementation is registered by `createRepo`, not by a module
    side effect (the package is `sideEffects: false`).
15. **Telemetry**: `insert`, `update`, `delete`, `insertAll` (one event per chunk),
    `updateAll`, `deleteAll`; `insertOrUpdate` reports the write it made. Redacted values
    appear as `**redacted**` with `log: { params: true }` (tested on Postgres for insert,
    update and insertAll).
16. **Database schemas** follow the adapter contract: per-call option, else the row's
    `RowMeta.schema` (update, delete) or the schema class's declared one (insert,
    insertAll), else the repo default. `updateAll`/`deleteAll` are queries (per-call option
    is the weakest position).
17. **Dialects without `RETURNING`** (spec item 7): a single generated key comes from
    `insertId` (through the field type's `cast`); when other fields are the database's, or
    `returning`/an upsert asks, the row is read back by key on the same connection, within
    the call's budget. Unit-tested over a fake driver only (no such adapter exists yet).

## Known gaps

- The no-`RETURNING` path (decision 17) runs only against a fake driver.
- When `timeoutMs` runs out during a later statement of a multi-statement call, the
  adapter's message says the statement ran longer than its `timeoutMs` and quotes what was
  left of the budget, not the call's `timeoutMs`.
- A unique constraint name Postgres truncated (over 63 characters) is not recognised as a
  default name: the message falls back to the `{ name }` form with `"<field>"`.
- `InsertAllRow` accepts a nullable expression for a non-nullable field (decision 10);
  the database refuses the `NULL`.

## Requests

**Steps 12 / 19 (`repo/read.ts`)** — step 09 asked that a `PreparedQuery` given to a read
use `prepared.plan(core.adapter, operation, schema)`. Done for `updateAll`/`deleteAll` in
`bulk.ts`; `read.ts` is not this step's file and `load` receives an AST, not the
queryable, so it is left for whoever next changes it.

**Step 15 (nested changesets)** — `checkNested` in `write.ts` refuses changes whose key is
not a field, or whose value is a changeset (or an array holding one), with "nested changes
are not supported yet". Replace it with `persistNested(cs, "before" | "after", tx)` and run
the prepare functions inside that transaction.

**Step 16 (transactions)** — a transaction repo is a `DatabaseRepo` over a `ReadCore` whose
`executor` is the connection; the writes run there unchanged, and `insertAll` with several
chunks then joins the caller's transaction without a savepoint (a failed chunk aborts it,
as any failed statement does). Decide whether `insertAll` should take a savepoint there.

**Step 17 (dialects)** — `insertAll` writes ragged rows with `DEFAULT` cells, which SQLite's
`VALUES` does not accept and no capability describes; add one (for example
`defaultInValues`) and have `insertAll` refuse ragged rows without it, listing the keys
(the spec's "else error"). The no-`RETURNING` path (decision 17) needs its first real test
on MySQL and SQLite; `insertId` is cast with the key field's type.

**Step 02 / owner (`errors.ts`)** — `StaleEntryError`'s message says "no row matched its
primary key and lock version" for every update, also when there is no lock.
