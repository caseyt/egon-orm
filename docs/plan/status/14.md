## Decisions

1. **Has-through is one statement** per level, not a preload of each step. The chain is
   joined backwards from the target, and the column of the first step that points at the
   owner is selected beside each row (`$o0`). This keeps "1 + levels", applies the
   callback's filters, order and per-parent limit to the target rows of each parent (a
   step-by-step load would order and limit per intermediate row), and loads nothing in
   between. A row reached along several paths is kept once per parent, by primary key
   (whole rows; a selected shape is kept as it comes, having no key).
2. **Per-parent `limit` / `offset`.** The callback's query, with the key filter, is ranked
   in a subquery (`row_number() over (partition by <owner key> order by <callback order,
   else the association's>)`), joined back to the target on its primary key (and on the
   owner key for joined routes), and filtered `rank > offset` and `rank - offset <= limit`
   (no parameter arithmetic: step 10's open bug with `$1 + $2`). It needs the target's
   primary key (`QueryError` otherwise), and it is refused on a has-through chain along
   which a row can repeat (a `belongsTo` or many-to-many step after the first), since the
   rank would count that row once per path.
3. **Errors before anything runs.** Besides step 08's build-time checks, the statement
   parts of every separate preload are built (and cached per `PreloadNode`) before the
   main statement is sent, so a preload that cannot run fails with nothing sent.
4. **Identity.** A target fetched once for several parents is given to the first as it is
   and copied for every later one: new rows (by their schema's factory, with their loaded
   associations copied too), new arrays and plain objects, new `Date`s and byte arrays.
   Values of a custom type (class instances) are shared.
5. **Canonical preload order.** The builder keeps preloads in the order the schema
   declares its associations, at every level (`sortPreloads` in `builder.ts`), so one set
   of preloads is one row shape whatever order it was asked in, as `repo.preload` (which
   merges with what is loaded) also builds them. Visible effects: the property order of
   loaded rows, `toString()`, and the order sibling preloads run in. Two existing tests
   (step 08's `toString`, step 10's output plan) were updated to the new order.
6. **The schema class comes first** in `repo.preload(User, users, "posts")`,
   `assoc(User, user, "posts")` and `isLoaded(User, user, "posts")`. TypeScript cannot get
   from a row's type (`User`, the instance type) to its class's static side, where the
   associations are declared, so `repo.preload(users, "posts")` could not check the name
   or type its result. (At run time the class is known from the row; the argument is
   checked against it.)
7. **`repo.preload` callbacks take values, not named parameters**: the callback runs at
   once, so a value can be written into it. A callback with `param(…)` is a compile error
   and a `QueryError`. (A preload callback of a *query* keeps its named parameters, which
   come with the query's; this is step 08's design.) The reason it is not supported is a
   TypeScript limit: a parameter after the callback stops the callback's query type from
   being inferred.
8. **`reload` re-preloads** (step 12's Request, the owner's answer in status 12; rebuilt
   in review round 1). Every row that preloads were run for remembers them: a root row of
   a query or of `repo.preload`, and every whole row a preload loaded with preloads below
   it, holds an entry in a `WeakMap` (one shared record per call and level: the preload
   nodes and the call's named values). `reload` loads exactly that record again on the
   fresh copy, callbacks (filter, order, limit, select) and named values included, at
   every depth, also below a level that was loaded empty; a join preload is loaded again
   by a separate query (the join's own conditions are not kept). `repo.preload` records
   what the row had plus what it added (`force` replaces), a copy for a later parent
   keeps the record of its original, and a row a write returns keeps the record of the
   row it was given (`keepPreloads`, review round 2). The record also holds the call's
   database schema, which a reload reads with unless it is given a `schema` option
   (review round 2). A record keeps the callbacks' queries and the call's named values
   alive as long as any of its rows (a `WeakMap` frees it with them). A row with no
   record (associations put on a row by hand) is reloaded by name, with what its loaded
   rows show. `timeoutMs` is one budget for every statement of a `reload`.
9. **Telemetry.** Every preload statement reports `operation: "preload"`, `source` the
   target's table, and the call's `context`; a throwing listener does not fail it (step
   12's hub).
10. **`maxConcurrency`** is a read option (every read, and `repo.preload`): how many
    preload statements of the call may run at once (sibling associations, at any depth).
    Default 1. On a connection (inside a transaction) always 1. A value other than a whole
    number of at least 1 is a `TypeError`.
11. **`timeoutMs` is one budget** for the whole call: the deadline is taken before the
    main statement, and each preload statement gets what is left; a preload statement
    stopped by it rejects with `DatabaseError` (`"timeout"`) quoting the call's
    `timeoutMs`, the adapter's error as `cause` (step 13's `overBudget`).
12. **Chunks.** At most 10,000 keys per statement; where lists are expanded (no array
    parameters), also no more than `capabilities.maxParams` allows beside the statement's
    other parameters. A composite key is matched as a row: `(a, b) in (select … from
    unnest($1, $2))` with array parameters, else a `values` list.
13. **Key matching in JavaScript** (grouping children by owner key; review round 1):
    every key part is looked up in a `Map` under a canonical primitive: primitives as
    they are, timestamps by time, decimals by the decimal type's own `canonicalDecimal`
    (`"1.50"` is `"1.5"`; review round 2, so the key and the type's `equal` agree), bytes
    by their hex string. Only a custom type's values are compared with its
    `equal`, in a list.
14. **Join preloads.** Merging needs the parent's primary key: a join preload on a schema
    without one is a `QueryError`. Children without a primary key are not de-duplicated.
    A join preload nested under a many-to-many or has-through preload is refused (its rows
    come out of an object select, which carries no join children).
15. **Named parameters** of a query with preloads are checked once, against every name the
    query and its preload callbacks use, before the first statement; each statement binds
    the ones it uses.
16. **Database schemas** (review round 1). Parents whose schema class declares no
    database schema are grouped by their `RowMeta.schema`, which is passed as the
    `schema` argument of their children's statement (the adapter contract). A parent
    whose class declares one was read from it whatever the call said, so its children are
    read with the call's own schema: the root query's `.schema(…)`, else the call's
    `schema` option, else the repo's default. `repo.preload` takes no `schema` option (a
    `TypeError`): each row says where it was read.
17. **`assoc()`**: a direct association filters the target's key fields (`= any`, or an
    `or` of `and`s for a composite key); a many-to-many or has-through filters the
    target's primary key by a subquery that follows the association from the parents
    (`joinAssoc`). The association's `where` applies; its `orderBy` does not.
18. **Types of `repo.preload`.** The result is the given row type with the loaded
    properties, which replace properties of the same name (a forced reload as a selected
    shape is typed as that shape).
19. **A limit with a to-many join preload** (review round 1). A `limit` or `offset` on the
    query, and `repo.first` (which adds one), would count the joined rows, not the
    parents, and cut a parent's children short. They are refused with a `QueryError`
    before anything is sent, pointing at a separate preload; a to-one join preload and
    separate preloads may be limited. The same holds for a preload callback's per-parent
    `limit` / `offset` when the callback join-preloads a to-many association (review
    round 2).
20. **Key redaction** (review round 1): a key value sent by a preload is redacted in logs
    when the field on either side of the association is redacted, for single and
    composite keys.
21. **A failed statement stops the run** (review round 1): with `maxConcurrency` above 1,
    the first failure (of a statement, or of decoding its rows) is recorded on the run,
    the statements waiting for a turn are woken and reject with it, and no later
    statement starts.

## Known gaps

- A row with no preload record (only one whose associations were put on it by hand) is
  reloaded by name: below a level its loaded values show empty, nothing is reloaded
  (decision 8). Every row a read, `repo.preload` or a write returns has a record.
- A join preload is reloaded by a separate query, without the join's conditions
  (decision 8).
- Children of a join preload without a primary key are not de-duplicated; a has-through
  loaded as a selected shape is not de-duplicated either.
- Copies for later parents share values of custom types (decision 4).
- The preload suite has run on Postgres 16 only.
- Per-parent limit on a has-through chain along which rows can repeat is refused, not
  supported.

## Review, round 1

The reviewer requested changes on PR #35 at `ab04413`: 10 findings, and accepted every
owner row (decision 8 once finding 7 is fixed). All were taken.

1. **Children of a parent whose class declares a database schema were read from it.**
   The run carries the call's own schema (root query's `.schema(…)`, else the `schema`
   option, else the repo default); a parent whose class declares a schema gives its
   children that one, other parents their `RowMeta.schema` (decision 16). Unit tests of
   the SQL (default, option, query schema, `repo.preload` with a repo default); a Postgres
   case with `AuthUser` in `auth` over a decoy `auth.posts` (fails without the fix,
   checked). Guide "Short forms" amended.
2. **`assoc()` over a has-through filtered on the first part of a composite owner key.**
   Both branches now use one `keysCondition` (every part: `= any` for one column, an `or`
   of `and`s for several). Unit test with a composite-keyed has-through (`Rack.items`).
3. **Quadratic key matching for decimals, bytes and custom types.** `KeyIndex` now maps
   decimals by their normalised digits and bytes by hex into its `Map`; only custom types
   use `equal` in a list (decision 13). Unit tests: `"1.50"` / `"1.5"` / `"01.500"`,
   `"-0.0"` / `"0"`, `"0.50"` / `".5"`, a value that is not a number, bytes; and a
   preload whose parent key is `"1.50"` and children's `"1.5"` / `"1.500"`. No timing test
   (benchmarks are step 19's).
4. **`repo.first` with a to-many join preload loaded one child.** A `limit` or `offset` on
   the query, or `repo.first`, with a to-many join preload at any depth of join preloads,
   is a `QueryError` before anything is sent, pointing at a separate preload (decision 19).
   Unit tests (first, limit, offset, a to-many join below a to-one join; to-one join and
   separate preloads still limited) and a Postgres case. Guide "From a join" says so.
5. **Key redaction depended on the side.** A key is redacted when the field on either
   side is (decision 20), in the single and both composite forms. Unit tests through
   `log: { params: true }`: `hasMany` from a redacted key, `belongsTo` to it, and a
   composite key with one redacted part.
6. **`repo.preload` ignored a `schema` option.** It is refused with a `TypeError`;
   `PreloadOptions` omits it and the guide says why (decision 16). Unit test.
7. **`reload` skipped levels loaded empty.** Rows now record their preloads (decision 8)
   and `reload` loads the record, so a level loaded empty is reloaded with what is below
   it. The owner row for decision 8 sets out both options (keep the callbacks, or names
   only); the recommendation, keeping the callbacks, is built. Unit tests (the empty level
   twice over, a callback's select re-applied, a row without a record) and the reviewer's
   case on Postgres (fails with the old inference, checked).
8. **Waiting statements started after a failure.** The run records its first failure
   (statement or decoding), wakes its waiting statements, and `turn()` rejects them and
   any later one (decision 21). Unit tests: with `maxConcurrency: 2` and three siblings,
   the first failing, no third statement reaches the driver; the same for a decoding
   failure, with and without listeners.
9. **`afterDecode` had no `@example`.** Added.
