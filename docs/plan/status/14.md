## What shipped

- `packages/core/src/repo/preload.ts`: the preload runtime.
  - `runPreloads` (step 12's `afterDecode`): merges the parents of join preloads, then runs
    the separate preloads, level by level.
  - `loadSeparate` / `loadGroup`: one statement per association level (per chunk of keys,
    per database schema of the parents), children grouped by owner key in a `KeyIndex` and
    attached; nested levels run once over all the children of a level.

    association's route, the key filter, the order, and for `limit` / `offset` a ranked

    target's key.

  - Copies for later parents (`copyValue`), `repo.preload` (`preloadRows`, `preloadInto`,

## Decisions

1. **Has-through is one statement** per level, not a preload of each step. The chain is
   joined backwards from the target, and the column of the first step that points at the
   owner is selected beside each row (`$o0`). This keeps "1 + levels", applies the
   callback's filters, order and per-parent limit to the target rows of each parent (a
   step-by-step load would order and limit per intermediate row), and loads nothing in
   between. A row reached along several paths is kept once per parent, by primary key
   (whole rows; a selected shape is kept as it comes, having no key).
2. **Per-parent `limit` / `offset`.** The callback's query, with the key filter, is ranked
   in a subquery (`row_number() over (partition by <owner key> order by <callback order,
   else the association's>)`), joined back to the target on its primary key (and on the
   owner key for joined routes), and filtered `rank > offset` and `rank - offset <= limit`
   (no parameter arithmetic: step 10's open bug with `$1 + $2`). It needs the target's
   primary key (`QueryError` otherwise), and it is refused on a has-through chain along
   which a row can repeat (a `belongsTo` or many-to-many step after the first), since the
   rank would count that row once per path.
3. **Errors before anything runs.** Besides step 08's build-time checks, the statement
   parts of every separate preload are built (and cached per `PreloadNode`) before the
   main statement is sent, so a preload that cannot run fails with nothing sent.
4. **Identity.** A target fetched once for several parents is given to the first as it is
   and copied for every later one: new rows (by their schema's factory, with their loaded
   associations copied too), new arrays and plain objects, new `Date`s and byte arrays.
   Values of a custom type (class instances) are shared.
5. **Canonical preload order.** The builder keeps preloads in the order the schema
   declares its associations, at every level (`sortPreloads` in `builder.ts`), so one set
   of preloads is one row shape whatever order it was asked in, as `repo.preload` (which
   merges with what is loaded) also builds them. Visible effects: the property order of
   loaded rows, `toString()`, and the order sibling preloads run in. Two existing tests
   (step 08's `toString`, step 10's output plan) were updated to the new order.
6. **The schema class comes first** in `repo.preload(User, users, "posts")`,
   `assoc(User, user, "posts")` and `isLoaded(User, user, "posts")`. TypeScript cannot get
   from a row's type (`User`, the instance type) to its class's static side, where the
   associations are declared, so `repo.preload(users, "posts")` could not check the name
   or type its result. (At run time the class is known from the row; the argument is
   checked against it.)
7. **`repo.preload` callbacks take values, not named parameters**: the callback runs at
   once, so a value can be written into it. A callback with `param(…)` is a compile error
   and a `QueryError`. (A preload callback of a *query* keeps its named parameters, which
   come with the query's; this is step 08's design.) The reason it is not supported is a
   TypeScript limit: a parameter after the callback stops the callback's query type from
   being inferred.
8. **`reload` re-preloads** (step 12's Request, the owner's answer in status 12): what a
   given row had loaded is loaded again on its fresh copy, by name, at every depth the
   given rows show, with the associations' own `where` and `orderBy`. A callback's filter,
   order, limit or select is not kept on a row and is not applied again (a selected shape
   comes back as whole rows); a level whose loaded values were all empty shows no deeper
   level, so nothing below it is reloaded. `timeoutMs` is now one budget for every
   statement of a `reload`.
9. **Telemetry.** Every preload statement reports `operation: "preload"`, `source` the
   target's table, and the call's `context`; a throwing listener does not fail it (step
   12's hub).
10. **`maxConcurrency`** is a read option (every read, and `repo.preload`): how many
    preload statements of the call may run at once (sibling associations, at any depth).
    Default 1. On a connection (inside a transaction) always 1. A value other than a whole
    number of at least 1 is a `TypeError`.
11. **`timeoutMs` is one budget** for the whole call: the deadline is taken before the
    main statement, and each preload statement gets what is left; a preload statement
    stopped by it rejects with `DatabaseError` (`"timeout"`) quoting the call's
    `timeoutMs`, the adapter's error as `cause` (step 13's `overBudget`).
12. **Chunks.** At most 10,000 keys per statement; where lists are expanded (no array
    parameters), also no more than `capabilities.maxParams` allows beside the statement's
    other parameters. A composite key is matched as a row: `(a, b) in (select … from
    unnest($1, $2))` with array parameters, else a `values` list.
13. **Key matching in JavaScript** (grouping children by owner key): primitive types by
    `===`, timestamps by time, other values (decimals, bytes, custom types) by their type's
    `equal`. Keys come from the database on both sides.
14. **Join preloads.** Merging needs the parent's primary key: a join preload on a schema
    without one is a `QueryError`. Children without a primary key are not de-duplicated.
    A join preload nested under a many-to-many or has-through preload is refused (its rows
    come out of an object select, which carries no join children).
15. **Named parameters** of a query with preloads are checked once, against every name the
    query and its preload callbacks use, before the first statement; each statement binds
    the ones it uses.
16. **Database schemas.** Parents are grouped by their `RowMeta.schema`, which is passed
    as the `schema` argument of their children's statement (the adapter contract).
17. **`assoc()`**: a direct association filters the target's key fields (`= any`, or an
    `or` of `and`s for a composite key); a many-to-many or has-through filters the
    target's primary key by a subquery that follows the association from the parents
    (`joinAssoc`). The association's `where` applies; its `orderBy` does not.
18. **Types of `repo.preload`.** The result is the given row type with the loaded
    properties, which replace properties of the same name (a forced reload as a selected
    shape is typed as that shape).

  `chunkKeys` lowered to 1,000 (three statements), because the shared Postgres VM is
  small (the coordinator asked to keep tests to a few thousand rows); the 10,000-key
  default (one statement for 10,000 keys, two for 10,001) is a unit test.
- **Preload inside a transaction**: step 16 (`repo.transaction`) is not merged, so the
  conformance case runs `load` on a `ReadCore` whose executor is one connection, inside
  `begin` / `rollback`: it sees the transaction's uncommitted rows, runs every statement
  on that connection, and one at a time even with `maxConcurrency: 4`. Request to step 16.
- No benchmark (deferred to step 19).
- No check was disabled, exempted or worked around; no dependency was added;
  `pnpm-workspace.yaml` is unchanged.

## Known gaps

- `reload` does not re-apply a preload callback, and does not reload below a level whose
  loaded values were all empty, although the row's type says those are loaded (decision 8).
- Children of a join preload without a primary key are not de-duplicated; a has-through
  loaded as a selected shape is not de-duplicated either.
- Copies for later parents share values of custom types (decision 4).
- The preload suite has run on Postgres 16 only.
- Per-parent limit on a has-through chain along which rows can repeat is refused, not
  supported.

## Requests

**Step 16 (transactions)** — a transaction-scoped repo's `ReadCore.executor` is the
connection, and preloads then run one at a time on it (`core.executor !== core.adapter`).
Add a conformance case through `repo.transaction` (the preload suite has one through
`load` on a connection, see Deviations).

**Step 15 (nested changesets)** — an association loaded as a selected shape holds plain
objects (`isRow` is false); `castAssoc` on it should throw `NotLoadedError`, as the step 14
spec says. `isLoaded(Schema, row, name)` tells a loaded association from one that is not.

**Step 17 (dialects)** — a profile for `runPreloadConformance` (`schema`, `insertUsers`,
`sleep`). The composite-key filter is `(a, b) in (select … from (values …))` without
array parameters, and per-parent limits use `row_number() over (…)` (SQLite 3.25+, MySQL
8).

**Step 19 (performance)** — the preload benchmarks of the spec. The level statement parts
are cached per `PreloadNode` (a query defined once reuses them; a query built per request
rebuilds them); children are grouped with one `KeyIndex` per level; parents after the
first get copies.
