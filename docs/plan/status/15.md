## Decisions

1. **Where a to-many change keeps its removed rows.** `cs.changes.comments` is the new
   items in the params' order, then a changeset for each row left out that `onReplace`
   acts on (`delete` → action `"delete"`, `setNull` → action `"update"` setting the foreign
   key to `null`). So positions in the list are the params' positions, which the error tree
   and issue routing rely on. A to-one change is the new child (or `null`); the row it
   replaces is read from the parent's data when the parent is saved.
2. **`onReplace: "error"` throws `QueryError` at cast/put time**, before anything is sent
   (a configuration error, not a validation one). `"invalid"` adds
   `{ message: "is invalid", validation: "replace" }` to the association.
3. **(owner) Many-to-many and `"delete"`.** The guide said "removing a many-to-many
   association deletes the join row only, unless `onReplace` is `"delete"`", while
   `onReplace` defaults to `"error"` and step 04 allows only `"error"`, `"invalid"` and
   `"delete"` there. Built: removing a link needs `onReplace: "delete"`, and it deletes the
   join row only; target rows are never deleted (they may be linked elsewhere). The guide
   now says so. Alternative: remove join rows without any `onReplace`, and delete target
   rows with `"delete"`.
4. **(owner) A duplicate key in the params** (two items with the id of one child) adds
   `{ message: "is invalid", validation: "duplicate", meta: { index } }` to the association
   (untrusted input), and the second item stays in its place as an insert so positions hold.
   In `putAssoc` (trusted data) the same row twice throws `QueryError`.
5. **Keys are cast** with the key field's type before matching (`"3"` matches `3`); a key
   the type rejects counts as absent (the item is new).
6. **No change.** When every item matches its child in order and changes nothing (and
   nothing is removed), the relation has no change, so `putAssoc` of the rows already there
   and a resubmitted unchanged form are no-ops. For a keyless embedded list, items equal to
   the stored ones are no change. Validity is worked out again from the errors and the nested
   changesets, so a nested change replaced by a valid one leaves the parent valid.
7. **To-one `update` and `null`.** `onReplace: "update"` cannot remove a `hasOne` or
   `belongsTo` row (`null` throws `QueryError`); for an `embedOne` it clears the field.
   `belongsTo` with `null` adds `can't be blank` to the association when its foreign key is
   not nullable. `belongsTo` with `setNull` leaves the old parent row as it is.
8. **`setNull` needs a nullable foreign key**; otherwise it throws `QueryError` at cast/put.
9. **`putAssoc` with a loaded row** of a `hasMany`/`hasOne`: kept as an update whose
   foreign key is set to the parent's when the parent is saved (so a row can be moved to
   this parent); for `manyToMany`, it is linked when not linked yet. A plain object may hold
   the child's own associations and embeds, put on the child in turn. `onReplace: "update"`
   with a plain object updates the to-one row there.
10. **Nested writes run through `atomically`** (step 16's request). Children of the same
    call run on that transaction as they are (no savepoint per level). An upsert
    (`onConflict`) with association changes is refused (`QueryError`): a row that is not
    inserted has no children. A prepare function that adds association changes to a flat
    changeset opens the transaction then (its own work before that is outside it).
11. **Order inside a to-many association**: rows leaving it (deleted, or key set to `null`),
    then updates, then inserts, so a unique value freed by one row can be taken by another.
    A replaced to-one child is deleted (or detached) before its successor is inserted. A
    replaced `belongsTo` target with `delete`/`deleteIfExists` is deleted after the parent
    stops pointing at it. `deleteIfExists` is a delete with `allowStale`.
12. **Database schemas of children**: an insert goes to the child class's declared schema;
    otherwise to where the parent went (the parent's call schema, row schema or the repo's
    default; when the parent class declares one, the call's own schema). Updates and
    deletes of loaded children go where those rows were read. Join rows: the join table's
    declared schema, else the parent row's.
13. **Failure shape.** The parent changeset (action set) with the failing child changeset in
    its place, carrying its errors and action; a parent's own handled constraint keeps its
    nested changes. Thrown errors (an undeclared constraint, a stale child, a database error)
    are rethrown after the rollback; a timeout of any statement is reported with the call's
    `timeoutMs`.
14. **The returned row** has each written association loaded (in the schema's declaration
    order, with the associations it had), rows that left it removed. The row's type does
    not show them (the changeset's type does not record which associations changed):
    narrow with `isLoaded`. The row keeps the preload record of the row it was written from;
    since cast and put need the association loaded, the record already names it.
15. **Errors on a key with children (step 05's request).** `traverseErrors` keeps both: a
    to-one child's tree gets `$errors` with the key's own errors; a list becomes
    `{ $errors, $items }`. Only when both exist; otherwise the shapes are as before.
16. **Validators see nested values (step 06's request).** The values object gets each
    association with a change as its children's values (the children that stay), and each
    embed with a change likewise; associations without a change are not added. Issues route
    by position among those children; `scope: "changed"` applies inside them; an issue that
    leads nowhere stays where it went before (field or `$base`). With `apply: true`, outputs
    for embed fields are not written back (Known gaps).
17. **Embeds.** An embed change is `cs.changes.address`: a child changeset (or `null`, or
    a list). `getField`, `fetchField`, `applyChanges` and `applyAction` give embedded rows;
    `getChange` gives the change. Embedded rows are `"built"` there and `"loaded"` once
    written. A keyed `embedMany` generates `.autogenerate()` keys (and timestamps; those
    with `insertAndUpdate` again on a changed item) when the row is built. A keyless list is
    replaced whole, whatever `onReplace`. Embed child `prepareChanges` functions and
    constraints are not run (there is no table).
18. **(owner) A stored embed missing a key of a field that is neither defaulted nor
    nullable** throws `CastError` on read, naming the field and the fix (give it a default).
    The alternative, `undefined` on a non-optional field, would break the row's type.
19. **`field()`** is a method on every expression, accepted by the types on an object-valued
    expression (embeds and `t.json` cannot be told apart in the types) and checked at run
    time: only a `t.embedOne` field. It reads `#>>` (text) cast to the field's type, or `#>`
    for a nested embed or JSON field so that it chains. The key is a bound parameter. A
    redacted embedded field makes the compared value redacted.
20. **(owner) `Col.field` is renamed `Col.fieldMeta`.** The column class had a public
    property `field` (its `FieldMeta`), which made the guide's `u.address.field("city")`
    impossible. `Col` is public as a type only; nothing in the packages read the property
    outside `expr.ts` and two tests.
21. **(owner) `buildAssoc` takes the schema class first** (`buildAssoc(User, user, "posts",
    values)`), as step 14's decision 6 did for `assoc` and `isLoaded`: a row's type does not
    lead back to its class. It builds `hasOne`/`hasMany` children only.
22. **Types of nested changes.** `Changes<S>` gains the association keys (child changesets)
    for a class whose associations the types know, and an embed field's change is typed
    `Changeset<E> | null` (or a list) **or the field's value**: the value is never there, but
    a changeset made from a row alone (whose types cannot tell an embed from another field)
    must still fit where a changeset of the class is expected, as step 05's tests require.
    `t.embedOne`/`t.embedMany` return `EmbedFieldBuilder`, which records the embedded class
    through `nullable`, `default`, `column`, `redact` and `writable`. On a changeset made
    from a row alone, nested names are any string and `with` is loosely typed.
23. **`with` is required** where the types know the target and it has no static
    `changeset` function (a compile error), and at run time otherwise (`QueryError`).

## Known gaps

- The type of the row a nested write returns does not include the associations it loaded
  (narrow with `isLoaded`).
- `putAssoc`'s plain-object type is structural: a row of another schema whose fields
  overlap passes the types and is refused at run time.
- `validate(…, { apply: true })` does not write a schema's output back into embed fields
  or associations.
- An association's `where` and a many-to-many's `joinWhere` are not applied to rows
  written through it (the association's `defaults`, always `undefined` today, are applied
  by `buildAssoc`).
- `castAssoc` on an association preloaded with a callback that filters it matches only the
  rows loaded: the others are neither updated nor removed.
- Unit branch coverage of the new files is 85–90% (lines 94–100%); the package thresholds
  (95%) are met. The remaining branches are mostly message variants.
- The nested suite has run on Postgres 16 only.

## Requests

**Step 17 (dialects)** — a profile for `runNestedConformance` (`schema` DDL for `orders`,
`line_items`, `contacts`). Embeds are written through the driver's `json` fix (Postgres
stringifies); a dialect that hands JSON back as text is parsed by the embed type itself.
`field()` emits `#>>` / `#>`: the dialect tables need their JSON path operators.

**Step 19 (performance)** — validators now build nested values when a changeset has nested
changes (one `for…in` over the changes otherwise), and the writes look for association
changes the same way. Embed fields are dumped and loaded through per-schema slot tables.

**Step 20 (docs)** — `reference/` has no page for the nested types (`CastNestedOptions`,
`PutItem`, …).
