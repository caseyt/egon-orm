## Decisions

1. **Shape.** A transaction repo is a `DatabaseRepo` over a `ReadCore` whose executor is a
   level (step 12's and 13's requests): the reads and writes run there unchanged. The root
   repo keeps a `RootScope`; repos are made through a factory passed from `repo.ts`, so
   `transaction.ts` does not import `repo.ts` at run time.
2. **(sign-off) A statement that fails inside a transaction ends it, on every database.**
   On Postgres a failed statement aborts the transaction until it, or a savepoint, is rolled
   back, and a `COMMIT` then silently rolls back. Egon records the first failure (an error
   from the database: `ConstraintError` or `DatabaseError`, also a cancelled statement) and
   from then on refuses every statement with a `QueryError` naming the cause. A callback
   that returns anyway gets `{ success: false, error }` with that statement's error
   (`RollbackError` from `transactionOrThrow`). A nested transaction undoes its own failure
   and the outer one carries on. Errors that never reached the database (a `TypeError`, a
   statement whose signal had fired, one that timed out while waiting in the queue) do not
   count. The same rule on MySQL and SQLite, where a failed statement does not abort the
   transaction, so that code behaves the same on every database.
3. **(sign-off) A failed `ROLLBACK`.** After a throw: the original error is rethrown with the
   rollback's failure as a non-enumerable `suppressed` property (when the thrown value is an
   extensible object without one), as the spec says. After `tx.rollback(reason)` or a failed
   statement: the rollback's failure is thrown (there is no other error to carry it). In
   both cases the connection is destroyed.
4. **A failed `COMMIT`** throws its error; the connection is released and, still inside a
   transaction by the driver's account, closed by the adapter (step 11). A failed `RELEASE`
   or `ROLLBACK TO` throws from the nested call and leaves the enclosing transaction able
   only to roll back as a whole.
5. **Nested options.** `isolation`, `readOnly` **and `retries`** on a nested transaction are a
   `QueryError` (the spec names the first two; a savepoint cannot be retried on a
   serialisation failure either, which aborts the whole transaction). `timeoutMs` is
   allowed: the nested one keeps the shorter of its own and its parent's budget.
6. **(sign-off) One nested transaction at a time.** While a nested transaction is open, a
   statement on the outer `tx` is a `QueryError` (it catches the outer `tx` used inside the
   inner callback, the same mistake as the root-use one, but here detectable); nested
   transactions started together take turns. A nested transaction still running, or a
   stream still open, when the callback returns rolls the transaction back with a
   `QueryError`.
7. **(sign-off) Use after completion** (spec item 5) is checked by the level, so it covers every
   call that reaches the database, and `transaction`, `rollback` and `checkout`. A call that
   never reaches the database (`toSql`, inserting an invalid changeset, an update with no
   change) does not throw. Statements issued before the callback ended and still queued run
   before the `COMMIT`; on a rollback they are not sent.
8. **`timeoutMs` is one budget** (owner decision): the wait for a connection, every
   statement and every retry. Each statement gets the shorter of its own `timeoutMs` and what
   is left. At the deadline the running statement is cancelled (through its `timeoutMs`), the
   transaction is rolled back at once, and the call rejects with `DatabaseError` (`"timeout"`)
   whose message quotes the transaction's budget, without waiting for the callback; the
   callback's later calls on `tx` are refused. A budget that ran out decides the outcome even
   when the callback caught the cancelled statement's error.
9. **The transaction statements** are the adapter's `Connection` methods (`begin`, `commit`,
   `rollback`, `savepoint`, `rollbackTo`, `releaseSavepoint`), which write each dialect's
   syntax. They take no options in the frozen contract, so `timeoutMs` does not cancel them
   (Known gaps), and **(sign-off)** they are not the repo's `query` events: `log: true` and
   `expectQueries` do not show them; the adapter's own `query` events do. The contract change
   that would fix both is proposed in
   [ADR 0005](../../adr/0005-transaction-statement-options.md) (status: proposed, not
   implemented).
10. **Retries** run on a retryable `DatabaseError` (`serializationFailure`, `deadlock`) that
    the callback threw, that `COMMIT` threw, or **(sign-off)** that ended a callback which
    caught it and returned (decision 2), and **(review round 1)** when the transaction had
    recorded such a failure whatever the callback then threw (a callback that catches a
    deadlock and runs one more statement throws the refusal's `QueryError`, whose cause it
    is). Not on `tx.rollback()`, not on other errors. Each
    attempt takes a new connection; the pause is `min(1 s, 10 ms · 2^attempt)` times a random
    factor in [0.5, 1.5); no attempt is begun whose pause would pass the deadline.
11. **`warnOnRootUseInTransaction`** (owner decision: development only, `AsyncLocalStorage`):
    installed by `createRepo` when the option is on and `NODE_ENV` is not `production`. The
    root's executor becomes a thin wrapper over the adapter that checks the store, and
    `AsyncLocalStorage` is obtained with `process.getBuiltinModule("node:async_hooks")` on
    first use, so `egon-orm` still has no static import of a Node module and no runtime
    dependency. The warning is `process.emitWarning(…, { code: "EGON_ROOT_IN_TRANSACTION" })`
    (packages may not use `console`), once per transaction, for root statements, streams,
    `transaction`, `checkout` and bulk writes made inside a transaction callback. Inside the
    sandbox the same mistake is an error, not a warning (decision 21). The store never
    propagates a transaction: it only tells a call from inside a callback.
12. **`ReadCore.pooled`.** The code of steps 12 and 13 told "runs on the pool" from "runs on
    one connection" by `executor === adapter`, which the warning's wrapper breaks. `ReadCore`
    has a `pooled` flag (set from that test, and by the wrapper and the sandbox); `write.ts`
    and `bulk.ts` read it.
13. **`inTransaction` and `rollback`.** `tx.inTransaction` is `true` (nested too, and on the
    sandbox's repo); the root repo's and a checkout's are `false`, the root's also while a
    sandbox routes it, as in production. `rollback()` on the root, a checkout or the
    sandbox's repo is a `QueryError`. `rollback(reason)` takes a reason (required by the types).
    The first reason wins when a callback catches the signal and calls it again.
14. **Checkout.** One connection, no statements of its own; statements it issued and did not
    await run before the connection goes back; refused afterwards. `r.transaction(fn)` inside
    it begins a real transaction on that connection, with every option and retries. On a
    transaction's repo, `tx.checkout(fn)` calls `fn(tx)`. Checkout takes no options.
15. **Streams** (spec item 8): `repo.stream` opens no transaction on Postgres, as step 12's
    approved decision 10 settled. On `tx`, a stream runs on the connection after the
    statements before it; other statements are refused while it is open (step 11's rule).
16. **`insertAll` inside a transaction (step 13's request): a savepoint.** Several chunks run
    through `atomically`: their own transaction on the pool (as before), a savepoint on a
    transaction's repo (so a failed chunk undoes the call alone and the transaction stays
    usable, like a standalone `insertAll`), `BEGIN`/`COMMIT` on a checkout's connection, and
    joined as they are on a connection a caller manages (step 13's test of that stays).
    One chunk is one statement and takes no savepoint, like `insert`. Spec item 9: step 15's
    nested writes should use `atomically` too (Requests).
17. **`RollbackError`** messages differ for an explicit rollback, a batch failure (naming the
    step) and an unhandled failed statement; `reason` is always what `transaction` returns as
    `error`; `cause` is set for the statement case.
18. **Batch names.** Non-empty strings (`TypeError` otherwise). A repeated name is a compile
    error where the types see it (a `Unique<N, R>` parameter type) and a `QueryError` when the
    batch is built (`append`, `prepend` included), or when a `merge` adds it at run time
    (checked against every name of the batch, later ones too). `inspect(name, fn)` takes a
    step name; `inspect(fn)` none. `merge` is one step in `toList`.
19. **Batch types.** `R` maps names to results (plain object, not `readonly`), `F` is the union
    of `BatchFailure<step, error, completed>` of the steps that can fail: the write steps
    (their changeset) and `run` (its `failure`'s type); `insertAll`, `updateAll`,
    `deleteAll`, `one`, `all`, `exists`, `put`, `inspect` cannot fail, they throw. A batch with
    no such step has `F = never`; **(review round 1)** so does a `run` step whose callback only
    returns `success(…)` (its `E` is `never`, and it adds no member). Query steps take named parameters and options as the
    repo's reads do; while TypeScript has not yet inferred the query a step function
    returns, its parameters count as none, so that the call is checked once it has
    (`StepArgs`).
20. **Batch running.** Steps receive a copy of the results so far. A `run` that does not
    return a `Result` is a `TypeError` (and does not compile). A failed write step or
    `failure(x)` calls `tx.rollback({ step, error, completed })`. The check before the
    transaction covers write steps given a changeset as it is; the first invalid one wins,
    with `completed: {}`, and nothing is sent (no `BEGIN` either, asserted on the adapter's
    events). `createBatch()` returns one shared empty batch (it is immutable). `Batch` has a
    private constructor.
21. **Sandbox basics.** `createSandbox` takes only a repo made by `createRepo` (`TypeError`
    otherwise); `begin()` returns a repo bound to the sandbox's transaction, refuses a second
    `begin` (`QueryError`), and swaps the root's executor; `rollback()` restores it first,
    then rolls back, and does nothing when not begun. A failed `BEGIN` returns the
    connection; a failed `ROLLBACK` destroys it and is thrown. The repo's transactions become
    savepoints of the sandbox's; **(sign-off)** their `isolation`, `readOnly` and `retries`
    are left out (app code under test should not throw because a test wrapped it), and
    concurrent ones take turns. **(review round 1)** In the sandbox the transactions'
    callbacks always run under the `AsyncLocalStorage` store (whatever
    `warnOnRootUseInTransaction` says; the sandbox is test-only):
    - a call on the repo itself (or the sandbox's repo) from **inside** one of its
      transaction callbacks (a statement, a stream, another `repo.transaction`, a bulk insert
      of several statements) is a `QueryError` that names the mistake. Outside the sandbox
      it would run on another connection, outside the transaction; on the sandbox's one
      connection it could only run inside the transaction (undone by its rollback) or wait
      for it (which waits for the call: the hang the reviewer found);
    - a statement or stream of the repo from **outside** the open transaction (a concurrent
      request) waits for it to end, as nested transactions take their turns, so that the
      transaction's rollback cannot take it along (the silent loss the reviewer found).
22. **(sign-off) The sandbox runs each statement made on its own level in a savepoint**
    (`egon_statement`): `SAVEPOINT`, the statement, `RELEASE`, or `ROLLBACK TO` on failure.
    Outside the sandbox those statements would each run alone, so a write the database
    refuses would undo only itself; inside one transaction, on Postgres, it would poison
    every later statement of the test (a duplicate-email test could not count the users
    afterwards). This keeps app code behaving as in production. Cost: two more statements
    per query, in tests only. Statements inside the repo's transactions follow the
    transaction rules (decision 2). Streams at the sandbox level are not wrapped.
23. **`egon-orm/testing`** is a public subpath: `exports["./testing"]` in
    `packages/core/package.json`, a `testing` entry and **`splitting: true`** in core's
    `tsup.config.ts`, so that the entries share one copy of the code (one class per class,
    one registry of root repos); without it the sandbox of `dist/testing.js` could not
    recognise a repo made by `dist/index.js` (decision D14's reason against two builds).
    Step 18 (#34, merged) set `splitting: true` for `egon-orm/migration` too; the merge keeps
    one setting and the four entries `index`, `migration`, `testing`, `internal`. The ESM and
    CommonJS smoke consumers both check it. Path mappings: `tsconfig.base.json`,
    `vitest.config.ts` (aliases before `egon-orm`'s, which would otherwise swallow them).
24. **`expectQueries`** returns the repo's `query` events emitted while `fn` ran (its
    transactions' too), in order, and removes its listener in `finally`.

## Known gaps

- **The transaction statements are not cancelled by `timeoutMs`**: `Connection.begin`,
  `commit`, … take no execution options in the frozen contract. A `COMMIT` that hangs waits.
  ([ADR 0005](../../adr/0005-transaction-statement-options.md), proposed.)
- **Not run on MySQL or SQLite** (step 17). The suite assumes the three isolation levels, a
  serialisation conflict between two connections, and Postgres-like statements in its
  profile; step 17 needs capability skips for those (Requests).
- In the sandbox, a statement made on the sandbox's own level does not count its wait in the
  queue against its `timeoutMs` (it runs as one unit with its savepoint statements). Tests
  only.
- Streams at the sandbox's own level are not wrapped in a savepoint: a stream the database
  refuses poisons the test's transaction.
- `deferrable` (in the adapter's `BeginOptions`) is not a transaction option, and there is no
  `signal` option on a transaction. Neither is in the spec or the guide.
