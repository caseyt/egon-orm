## What shipped

  attach, readonly, planCacheSize })` over `better-sqlite3`.
  - `driver.ts`:
    - a pool of one handle, handed to one caller at a time in FIFO order, so two
      transactions never interleave;
    - safe integers, given back as numbers where they fit;
    - a prepared-statement cache of 500;

  - `errors.ts`: `normalizeSqliteError`.

## Decisions

1. **Arrays are stored as JSON** on SQLite and MySQL, and the array operators are refused.
2. **SQLite has one handle.** Callers queue for it. A connection released with `destroy`
   has its transaction rolled back, instead of the handle being closed.
3. **MySQL uses `-FOUND_ROWS`.** An `UPDATE`'s count is read from its info text by
   position, so it does not depend on the message language. The session is also pinned
   to `en_US`.
4. **MySQL upserts take no target** (`conflictTarget: false`, as the spec says). On a
   database without `RETURNING`, an upsert that meets a row it cannot read back is undone
   and throws.
5. **SQLite row locks are accepted and not written**, as the spec says.
6. **MySQL migration `text` is `varchar(255)`.**
7. **`sourceColumnList`**: SQLite refuses a column list on a fragment source. Only the
   repo builds fragment sources (`unnest`, Postgres only).
8. **Begin refusals name the dialect.**
9. **`timeoutMs` is checked between statements**: a statement whose budget is spent is
   refused with `"timeout"` before it is sent. This applies to every dialect; on Postgres
   and MySQL it replaces a 0 ms cancel.
10. **SQLite migrations lock with `begin immediate`** for the whole run, with savepoints
    per migration. This is step 18's request, implemented here.
    - A `transaction: false` migration runs outside the lock. The runner records a claim
      (version `-1` in the tracking table) and commits. It runs the migration with no
      transaction, then takes the lock again, removes the claim and records the version.
    - A runner that gets the lock while a claim is recorded gives it back and waits.
    - So two runners never both run it: the claim is written inside the lock before the
      lock is released, and every runner checks for it inside the lock before it reads
      the applied versions.
11. **uuids are written in lowercase** on SQLite and MySQL, as Postgres stores them. A
    returned row keeps the value given, as on Postgres.
12. **`sqlite({ attach })`**: a new option (public API), so that the one handle can see
    the database schemas.

## Review, round 2

The verdict on `e3cfade` was CHANGES REQUESTED, with 4 findings. The reviewer confirmed on
the real databases that every round-1 fix holds.

1. **SQLite `transaction: false` migrations ran inside the lock's transaction.** Fixed
   with a claim; the design is in decision 10 and in the owner table.
   - Such a migration now runs with no transaction while the runner's claim (version
     `-1`) is recorded, and other runners wait for the claim.
   - The failure message ("it ran without a transaction, so the statements before the
     failing one stay applied") is now true there.
   - Tests:
     - migration conformance "a migration with transaction: false runs outside any
       transaction" (`vacuum` on Postgres and SQLite) and "two runners at once apply a
       migration without a transaction once, 20 times in a row", on all three databases;
     - `sqlite/test/migrations.itest.ts`: the `foreign_keys = off` table rebuild, and a
       recorded claim that makes a runner wait, give up after `lockTimeoutMs` and then run
       once the claim is gone;
     - `migration/transaction-lock.test.ts`: the statement sequence, the failure path, the
       back-off on a claim, and the timeout message.
   - Mutations checked:
     - Running the migration inside the lock again fails the conformance `vacuum` case and
       the rebuild.
     - Ignoring claims fails the claim test.
   - The 20-round race does **not** catch ignored claims in one process. The first
     runner's SQLite statements are synchronous, and its steps chain through promises, so
     the other runner's retry timer cannot fire inside the window. The race needs two
     processes, which the recorded-claim test stands in for.
2. **The guide said SQLite takes no lock.** Fixed: `guide/migrations.md` now covers
   - the `begin immediate` lock and the 25 ms retry until `lockTimeoutMs`;
   - that other writers wait for the whole run (`SQLITE_BUSY` after their `busy_timeout`);
   - the savepoints;
   - how `transaction: false` runs under a claim, and what to do about a stale one.
3. **ADR 0006 wording.** Fixed: seven capabilities are checked at compile time, and two
   (`readOnlyTransactions`, `deferrableTransactions`) by `begin()`.
4. **The flaky preload test.** Moved from Known gaps to a Request to step 19.
