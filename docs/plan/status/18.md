# Step 18: Migrations and CLI, status

Branch `step/18-migrations-cli`. Built ahead of steps 14, 16, 17 and 21 at the owner's
request; Postgres is the only dialect with an adapter, so it is the only one migrations run
on (step 17 adds the MySQL and SQLite tables, see Requests).

## What shipped

- **`egon-orm/migration`**, a new public subpath of `egon-orm` (`packages/core/src/migration/`):
  - `defineMigration({ change })` or `({ up, down? })`, with `transaction` (default `true`).
  - The recorder `m` (`builder.ts`): `createTable`, `alterTable` (`add`/the column methods,
    `modify(name, type, { from, notNull, default })`, `remove(name, type?, options?)`,
    `rename`), `dropTable(name, define?, options?)`, `renameTable`, `createIndex` /
    `dropIndex` (`unique`, `where`, `using`, `concurrently`, `include`, `name`, `schema`,
    `ifNotExists` / `ifExists`), `createConstraint` / `dropConstraint` (`check`, `exclude`,
    `using`), `execute(up, down?)`, `createSchema` / `dropSchema`, `createExtension` /
    `dropExtension`. Arguments are checked when they are recorded (`TypeError` at the line
    that made the mistake).
  - Column methods named after the `DbType` kinds (`integer` … `jsonb`, `array`, `custom`,
    `add(name, type)`), plus `string` (= `text`), `id`, `references`, `enumText` and
    `timestamps`; builders `.notNull()`, `.nullable()`, `.default()`, `.primaryKey()`,
    `.unique()`.
  - The DDL emitter (`ddl.ts`): one function per operation, every identifier quoted by the
    compiler's dialect table, type names from that table (or a `custom` `sql` that matches
    `CUSTOM_SQL_TYPE`), keywords, reference actions and index methods from the new
    migration dialect table (`dialect.ts`). Fragments are compiled by the adapter's
    `compileFragment`; in DDL they may not bind values. `m.execute` binds its values.
  - The reversal of `change` (`reverse.ts`), refused at rollback time with the fix.
  - Default names (`names.ts`) that the changeset constraint defaults look for, shortened
    the way Postgres shortens its own when too long.
  - The runner `createMigrator({ adapter, directory | migrations, table, schema,
    timestampColumn, lockTimeoutMs, timeoutMs, log })` with `up`, `down`, `status`, dry
    runs, a session advisory lock, one transaction per migration, out-of-order warnings,
    and the `missing` state that blocks rolling back past it (`migrator.ts`).
  - Loading from a directory with `import()` (with the TypeScript-loader explanation) or
    from an in-memory list (`loader.ts`); `parseMigrationFileName`.
  - `createDatabase` / `dropDatabase` (`database.ts`), for `egon db`.
  - `MigrationError` (code `"migration"`, fields `version`, `migration`, `sql`) in
    `errors.ts`, exported from `egon-orm/migration`.
- **`@egon-orm/cli`** (`packages/cli/`): the `egon` binary (`dist/bin.js`) with

## Decisions

1. **(sign-off) No DDL method on the `Adapter` contract.** The spec says this step adds
   one. Options: (a) as built: the DDL emitter lives in `migration/` and reads the
   compiler's SQL table for the adapter's `dialect` (`sqlDialectOf`, quoting and type
   names) and a migration dialect table (DDL features and keywords); the adapter is used
   only through its public members (`compileFragment`, `acquire`, `capabilities`); (b) add
   `compileDdl(op)` to `Adapter` (a frozen contract, step 02) and to `createAdapter`
   (step 11). (a) changes no contract, keeps the DDL emitter out of the main bundle (it is
   in `dist/migration.js`), and does not oblige every `Adapter` implementation (test fakes
   included) to emit DDL. SQL text still comes only from tables, so ADR 0003's rules hold.
   Recommended: (a).
2. **(sign-off) Where the DDL capabilities come from.** The owner's rule is that
   *capabilities come from the dialect package* (`@egon-orm/postgres` declares
   `POSTGRES_CAPABILITIES`), and *SQL syntax from the compiler table*. As built the DDL
   capabilities have a **split source**:
   - `ddlTransactions` comes from the adapter's `Capabilities`, that is from the dialect
     package, as the rule says;
   - `concurrentIndexes`, `partialIndexes`, `includeColumns`, `exclusionConstraints`,
     `schemas`, `extensions`, `dropCascade` and `indexMethods` are hard-coded in core, in
     the migration dialect table (`migration/dialect.ts`), chosen by `adapter.dialect`. A
     dialect package cannot declare or change them, and step 17 has to edit this step's
     file to add its dialects (see Requests).

   Options:
   - **(a) As built.** The table sits beside the compiler's SQL tables, which are also in
     core and keyed by dialect, and it also holds DDL syntax (serial types, reference
     actions, the literal writer, the lock statements), which the rule puts in core. No
     contract change. Cost: the departure from the rule above for the eight flags, and the
     split source.
   - **(b) Optional DDL fields on `Capabilities`**, set by the dialect package:
     `readonly ddl?: { concurrentIndexes: boolean; partialIndexes: boolean; includeColumns: boolean; exclusionConstraints: boolean; schemas: boolean; extensions: boolean; dropCascade: boolean; indexMethods: readonly string[] }`,
     filled in `@egon-orm/postgres`'s `POSTGRES_CAPABILITIES` (and step 17's), with the
     migration table keeping only syntax. The emitter would read `adapter.capabilities.ddl`
     and refuse migrations when it is missing. Cost: a change to a frozen contract (step
     02) and to the dialect packages (steps 11 and 17), outside this step's paths.

   Recommendation: (a) for now, because it needs no contract change while the dialect
   packages are being written in parallel, with (b) as the move to make if the owner wants
   the rule to hold for DDL too; it is a mechanical change (the flags move, the emitter
   reads them from the adapter). The owner decides.
3. **(sign-off) Constants in DDL are written as literals.** DDL cannot take bound
   parameters (Postgres refuses `DEFAULT $1`), so a constant default and the allowed values
   of `enumText` are written by `MigrationDialect.stringLiteral`. Only strings, finite
   numbers, bigints, booleans and `null` are accepted (and, for `json`/`jsonb`, JSON
   values, written as their JSON text); anything else is a `TypeError`, and a string with a
   NUL or a lone surrogate (which has no UTF-8 form and would come back as U+FFFD) is
   refused, when recorded and again when emitted. On Postgres a string is `'…'` with every
   quote doubled, and `E'…'` with every backslash doubled as well when it holds a
   backslash, so the literal is the same under either setting of
   `standard_conforming_strings`. Evidence: a property test of a model of the lexer reads
   2,000 generated literals back under both settings, and the conformance suite reads
   tricky defaults (and `enumText` values) back from real Postgres under **both** settings,
   the second with `set local standard_conforming_strings = off` in the migration's
   transaction (review round 1). **Assumption:** the statement reaches the server in UTF-8
   (the `pg` driver sets `client_encoding` to UTF-8 at connect); under an encoding such as
   SJIS or GBK a multibyte character can end in the byte of a backslash or quote, and
   escaping by characters is not safe. The `stringLiteral` TSDoc says so. These constants are program text (the migration file), the same trust
   as a fragment's static strings, but they are a second exception to "every literal is
   bound" beside `custom.sql`. Other options: (b) defaults only as fragments (the
   developer writes the quoted literal by hand), (c) let the server quote them
   (`select quote_literal($1)` before each statement: an extra round trip, and a dry run
   needs it too). Fragments in DDL (defaults, predicates, constraints) may not bind values:
   refused when recorded and again when emitted. Recommended: (a), as built.
4. **(sign-off) The migrator takes the adapter, not the repo.** The spec says
   `createMigrator({ repo, … })` and a config exporting `{ repo, migrations }`. The repo
   does not expose its adapter (it is a private field of `DatabaseRepo`, step 12), and the
   runner needs `acquire()` for a dedicated connection (a session lock across several
   transactions), which the repo does not offer. Taking the repo would mean an internal
   accessor in `repo/repo.ts`, which step 16 is changing now. As built:
   `createMigrator({ adapter })`, config `{ adapter, migrations, database }`; the same
   adapter can be shared with `createRepo`. Recommended: keep `adapter`; a `repo` option
   could be added later if the repo grows an adapter accessor.
5. **(sign-off) No per-migration `lock` option.** The spec's example has `lock: true`.
   The runner holds a session-level advisory lock for the whole run; it takes no
   transaction, so `CREATE INDEX CONCURRENTLY` runs under it (tested), and there is nothing
   a migration would need to opt out of. `defineMigration` refuses unknown keys, `lock`
   included. The wait is bounded with the migrator's `lockTimeoutMs`. Recommended: accept.
6. **(sign-off) `createTable` requires a primary key unless `primaryKey: false`.** There is
   no implicit `id` column (explicit over inference): `t.id()` or `.primaryKey()` columns
   give the key, and `{ primaryKey: false }` declares a table without one. A table with
   neither is a `TypeError`; `primaryKey: false` with a key column too.
7. **(sign-off) Operations whose inverse could destroy something are irreversible in
   `change`**: `createTable`, `createIndex`, `createSchema`, `createExtension` with
   `ifNotExists` (the object may have existed before), `dropTable` / `dropIndex` /
   `dropConstraint` / `dropSchema` with `ifExists` or `cascade`, and `dropExtension`. They
   are refused at rollback with the fix (write `up`/`down`). The spec's list (`remove`
   without a type, one-argument `execute`, `modify` without `from`, `dropTable` without a
   definition) is covered too, and `modify` that changes `notNull` or `default` needs them
   in `from`.
8. **Columns follow SQL: nullable unless `.notNull()`**, as the spec's example
   (`t.string("email").notNull()`). Schema fields are the other way round (D3); the guide
   says so in its Good-to-know box.
9. **Column method names are the `DbType` kinds** ("Column builders mirror `DbType`"), so
   `t.timestamp` is without a time zone and `t.timestamptz` with one, while the schema's
   `t.timestamp()` is stored as `timestamptz`. Also stated in the box. `t.string` is kept
   as another name for `text` (the spec's example uses it).
10. **Names.** Unique index `<table>_<columns>_key`, other index `<table>_<columns>_index`
    (the blog fixture's `posts_author_id_index`), foreign key `<table>_<column>_fkey`,
    `enumText` check `<table>_<column>_check`. A primary key is left to the database to
    name. Explicit names are written in the DDL; a default name longer than 63 bytes is
    shortened with the repo's `shortenedName` (the rule Postgres uses for its own names).
11. **The tracking table** is `schema_migrations (version bigint primary key, created_at
    timestamp(0))`, filled with `now() at time zone 'utc'`. To adopt a table whose
    timestamp column is `inserted_at`, the migrator takes `timestampColumn: "inserted_at"`
    (explicit); without it, an existing table lacking `created_at` is refused with that
    hint before anything runs. The table is created under the lock; status and dry runs
    never create it.
12. **The lock** is `pg_advisory_lock($1, $2)` with two bound 32-bit keys: one for the
    library and one for the tracking table's database schema and name (the statements are
    in the migration dialect table). The keys are a contract between versions (two
    versions of an application in one rolling deploy must take the same lock), so they
    come from a fixed FNV-1a of their own (`migration/lock.ts`), not from the plan cache's
    hash, and a test pins their values (review round 1). The lock is released in
    `finally`; when the lock statement itself fails (including a timeout, after which the
    lock may still have been granted), or the release or a `ROLLBACK` fails, the
    connection is destroyed instead of pooled, which ends the session and its lock.
13. **Versions are numbers** (14 digits fit a safe integer), `to` is inclusive in both
    directions, `down` defaults to `step: 1`, and a recorded version without a migration
    blocks a rollback that would pass it before anything runs.
14. **Migration files** are `<14 digits>_<name>.<ts|mts|js|mjs>`; other files are ignored, a
    digits-and-underscore name with another number of digits is refused, two files with
    one version are refused. A file's migration is its default export or its export named
    `migration` (the docs examples use the latter, as this repository forbids default
    exports outside config files). `node:fs` is imported lazily, so an in-memory list
    works without a file system.
15. **Build.** `egon-orm` now builds with `splitting: true`, so `dist/index.js` and
    `dist/migration.js` share chunks and therefore one copy of every class (`EgonError`,
    `Expr`; `instanceof` works across the two entries, checked by the smoke test).
    `dist/internal.js` shares them too. `MigrationError` is exported from
    `egon-orm/migration` only, not from `egon-orm` (no change to the shared `index.ts`;
    `isEgonError(e, "migration")` works anywhere).
16. **CLI output.** Log lines on stdout, warnings and errors on stderr, `--json` one object
    on stdout (`ok: true | false`). A failed statement is printed; database messages are
    printed as the adapter normalised them, which (step 11) leaves out the driver's text
    because it may quote a value, so a failed migration shows `SQLSTATE 22012` rather than
    "division by zero". A `caused by:` line is printed only when the cause is itself an
    Egon error, never a driver's error (review round 1). `db drop` is `DROP DATABASE IF EXISTS`; `db create`, `drop` and
    `reset` all refuse with `NODE_ENV=production` unless `--force`, checked before the
    config is read.
17. **TypeScript loading** is not done by the CLI itself: it imports the config and
    migrations, and on `ERR_UNKNOWN_FILE_EXTENSION` explains the options (Node 22.18+, or
    `--experimental-strip-types` on 22.12 to 22.17, tsx, Bun, or JavaScript files). No
    loader is installed or registered behind the user's back.
18. **`--from-schema`** imports the file, takes its schema classes with a table (all of
    them must be named with `--export` when there is more than one) and writes a
    `createTable` per class from `meta()`: column types, `notNull`, constant defaults
    converted with the type's `toDb` (a mapped enum's stored value), primary keys, `t.id()`
    for a database-generated integer key, `t.references` for each `belongsTo`; comments for
    unique indexes, enum values and values the application or the database generates. The
    file and the command's output say it is a one-time scaffold, not a diff. Decimal
    precision and scale and timestamp precision are read from the type's name
    (`decimal(10,2)`, `timestamp(us)`), see Requests.

## Deviations from the spec

- `createMigrator` and the config take `adapter`, not `repo` (decision 4).
- No `lock` option on a migration (decision 5).
- No DDL method on `Adapter` (decision 1); DDL capabilities are not in `Capabilities`
  (decision 2).
- MySQL `GET_LOCK` and SQLite `BEGIN IMMEDIATE`, and the "half-applied on MySQL" note, are
  not built: there are no MySQL or SQLite adapters yet. The migration dialect table is the
  place for them (Requests, step 17). The guide documents Postgres's behaviour and says a
  migration without a transaction may be partly applied.
- "Failing migration rolls back cleanly on Postgres/SQLite": Postgres only, for the same
  reason.
- Paths outside the step's own, each minimal:
  - `packages/core/src/errors.ts`: the `MigrationError` class and the `"migration"` code
    (plan README §11 and step 02 assign `MigrationError` to this step).
  - `packages/core/package.json` (`exports["./migration"]`), `packages/core/tsup.config.ts`
    (the entry and `splitting: true`), `tsconfig.base.json` and `vitest.config.ts` (the
    `egon-orm/migration` path and alias): needed for the subpath. `vitest.config.ts` also
    gains a 95% lines/branches threshold for `packages/cli/src` (review round 1: a check
    strengthened, as plan README §6 asks for every package).
  - `packages/postgres/test/migration-conformance.itest.ts` and `migration-profile.ts`:
    the Postgres run of the conformance suite, as for the read and write suites.
  - `examples/smoke/esm.mjs`, `require-esm.cjs`: load `egon-orm/migration` (ESM and
    `require`) and check it shares classes with `egon-orm`.
  - `docs/site/.vitepress/config.ts` (sidebar entries), `docs/site/tsconfig.json` and
    `docs/site/package.json` (the CLI package for the config example),
    `docs/site/examples/migrations.ts` and `egon.config.ts` (new),
    `docs/site/reference/errors.md` (one row).
  - `pnpm-lock.yaml`: workspace links only (`@egon-orm/postgres` and `pg` for the CLI's

## Known gaps

- Only Postgres has a migration dialect table; the other dialects throw `MigrationError`
  from `createMigrator` until step 17 adds theirs.
- `packages/cli/src/bin.ts` (one line, `process.exitCode = await run(argv)`) is not covered
  in process; it is what `cli.itest.ts` runs. `packages/cli` as a whole is at 98% lines and
  96% branches, under the 95% threshold added in review round 1.
- The real-Postgres test of finding 1 (a lock timeout that fires as the lock is granted)
  depends on timing: with `lockTimeoutMs: 0` the timeout fires on this machine every time,
  and the test failed with the fix removed; on a slower server the race might not happen,
  and the test then passes without exercising it. The unit tests check the same rule
  deterministically.
- The CLI integration test builds `core`, `postgres` and `cli` with tsup in its `beforeAll`
  (about 5 seconds), because the integration job does not build.
- attw reports `egon-orm/migration` as unresolvable under `node10` (no `exports` support);
  that resolution mode is ignored by the `esm-only` profile, as for the main entry's
  CommonJS modes.
- `m` has no way to read data in a migration (no repo inside migrations); data changes are
  `m.execute` statements.
- `modify` writes `ALTER COLUMN … TYPE` without a `USING` clause; a conversion Postgres
  cannot do implicitly fails, and needs `m.execute`.

## Requests

- **Step 17 (dialects):** add MySQL and SQLite entries to the migration dialect table
  (`packages/core/src/migration/dialect.ts`, owned by step 18): their DDL features
  (no concurrent indexes, no exclusion constraints, SQLite without schemas and with
  limited `ALTER TABLE`), serial types, literal writers (MySQL's backslash escapes), lock
  statements (`GET_LOCK` / `RELEASE_LOCK`, SQLite `BEGIN IMMEDIATE`), `tableExists` /
  `columnExists`, `utcNow`; and the dialect branches the emitter may need as table fields
  (for example MySQL's `MODIFY COLUMN`). Then add profiles to run the migration
  conformance suite on both. MySQL has no transactional DDL
  (`ddlTransactions: false`), which the runner already honours.
- **Step 03 (types):** the `--from-schema` scaffold reads decimal precision/scale and
  timestamp precision from the type's `name`. Status 03 named a lookup beside
  `elementTypeOf` as the place for them as data; with one, the CLI would use it.
- **Step 16 (transactions):** if the repo gains a public way to reach its adapter, the
  migrator can accept `repo` as the spec wrote (decision 4).
- **Step 20 (docs):** `reference/roadmap.md` still lists "Migrations and a CLI" as planned
  after the first release; update it when this ships, and cross-link the new pages.
- **Step 21 (release):** decide whether `@egon-orm/cli` is published (it is still
  `private`) and add it to the shared version.

## Follow-up: up and down only

Owner decision, 2026-10-20: "Get rid of the "change" migration function. … up and down are
both required. User can just put a `// noop` comment if they don't want to do anything.
Update the template as well." Branch `step/18-up-down-only`.

### What changed

- **`defineMigration({ up, down, transaction? })`**: both functions are required. The
  definition type is `MigrationDefinition` (it replaces `ReversibleMigration` and
  `UpDownMigration`); `Migration.up` and `Migration.down` are no longer optional and
  `Migration.change` is gone.
  - A definition without `up` or `down` is a **type error**. `down() {}` with no parameter
    type-checks, and is the form the docs use when there is nothing to undo (Biome's
    `noUnusedFunctionParameters` warns on an unused `m`, and `pnpm lint` fails on warnings).
  - At run time (JavaScript, or a cast) `defineMigration` throws a **`MigrationError`**:
    `defineMigration() was given no down(). A migration has both up(m) and down(m); when
    there is nothing to undo, write down() {} with a // noop comment.` (`no up()`, or `no up()
    and no down()`). A definition with `change` gets `change() is not supported: write the
    change in up(m) and what undoes it in down(m).` instead of the second sentence, or, with
    `up` and `down` beside it, the usual unknown-key `TypeError` with the same hint. Wrong
    types (`up: "x"`, a non-boolean `transaction`) stay `TypeError`s.
  - **Loading** a file: when its import throws that `MigrationError`, the loader reports
    `Cannot load the migration file "<path>": defineMigration() was given no down(). …`, with
    `version` and `migration` set. A migration object that has the mark but lacks a function
    (made by another copy of the package, or forged) is refused after loading with `The
    migration file "<path>" has no down(). …`; `migrationList` does the same for an in-memory
    entry (`The migration "<name>" has …`). Every command that loads (`egon migrate`,
    `rollback`, `migrations`) exits 1 with that message.
- **Rollback always runs `down`.** `migrator.ts` runs `up` or `down` by direction; the
  refusal "it has up() and no down()" is gone, since such a migration cannot load.
- **`egon migrate create`** writes:
  ```ts
  import { defineMigration } from "egon-orm/migration";

  export default defineMigration({
    up(m) {
      // the change
    },
    down(m) {
      // undo it, or leave a // noop comment
    },
  });
  ```
- `transaction: false`, the locks, the SQLite claims and everything else are unchanged.

### What was removed

  of every operation and every "cannot be rolled back" refusal: `remove` without a type,
  `modify` without `from` or with an incomplete `from`, one-argument `execute`, `dropTable`
  and `dropConstraint` without a definition, and the `ifNotExists` / `ifExists` / `cascade`

  | `t.modify(name, type, { from })` | the previous type, `notNull` and `default` | `modify(name, type, { notNull?, default? })` |
  | `m.execute(up, down?)`: the second fragment | the statement that undoes it | `m.execute(sql)`; the undoing statement goes in `down` |
  | `m.dropTable(name, define?, options?)`: `define`, and the `primaryKey` option | the definition to recreate the table | `m.dropTable(name, options?)` with `schema`, `ifExists`, `cascade` |

  | `m.dropIndex(…, { where, using, include })` | the rest of the definition, to recreate it | new `DropIndexOptions`: `unique`, `name`, `concurrently`, `schema`, `ifExists`. The table, the columns, `unique` and `name` still name the index, as in the `createIndex` it undoes; `IndexOptions` is now `createIndex`'s only, without `ifExists` |
