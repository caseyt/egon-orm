## What shipped

### Part 1: one `json` flag

- `FieldFlags` and `FieldMeta` have `json` (default `true`). `.redact()` and `.virtual()`
  set it to `false`; `.virtual({ json: true })` leaves it as it is, so a redacted field stays
  out of JSON whatever the order of the modifiers (`.virtual({ json: true }).redact()` and
  `.redact().virtual({ json: true })` both give `false`, at run time and in the types).
- New types `WithoutJson<F>` (what `.redact()` and `.virtual()` apply) and `VirtualOptions`;
  `.virtual()` has two overloads (`{ json?: false }` and `{ json: true }`) and refuses other
  options with `SchemaDefinitionError`. `DefaultFieldFlags`, `WithFlag`'s examples, every
  hand-written flags type in source and tests, and every hand-built `FieldMeta`
  (`schema.ts`, `changeset/spec.ts`, tests) were updated.

### Part 2: `toJSON` returns the JSON-ready shape (the virtual-field leak is fixed)

- New `packages/core/src/schema/json.ts`. A row's `toJSON` is now built from a table made
  once per schema (`Meta.jsonTable()`, cached like `assocs()`): the fields whose `json` flag
  is true, in declaration order, each with a converter chosen once from its type's storage
  kind, or none for a value that is JSON already (text, uuid, decimal, time, boolean, enum,
  `t.date()`), skipped by reference. Then the row's own properties after its fields (its
  preloaded associations), each mapped as `JSON.stringify` would map it.
- The value table of the spec, every row: timestamps to `toISOString()`;
  `t.date({ as: "date" })` to `"YYYY-MM-DD"`; `t.bigint()` to a decimal string; numbers with
  `NaN`/`±Infinity` to `null` (and `-0` to `0`, so that the round trip deep-equals);
  `t.binary()` to base64 (the existing `toBase64` in `types/embed.ts`, no dependency);
  `t.json`, arrays and embeds element by element / field by field; a custom type through
  its own `toJSON`, else mapped by its value. An invalid `Date` is `null`, as
  `Date.prototype.toJSON` makes it.
- A class's own `toJSON` still replaces the default at every level; its result is mapped as
  `JSON.stringify` maps it (so a `Date` it returns is a string in `toJSON()` too).
- A changeset's `toJSON()` leaves every field whose `json` flag is false out of `changes`
  (so `JSON.stringify(cs)` after a sign-up no longer holds the password), maps the values as
  a row's do, writes nested changesets as JSON, and maps `errors` so that a `bigint` in an
  error's `meta` (`validateNumber` with `bigint` bounds) is a decimal string instead of a
  throw.
- Tests (`schema/json.test.ts`, 42 tests, 100% of `schema/json.ts`; updated
  `schema/schema.test.ts`): each row of the table; a row with every built-in type through
  `JSON.stringify`, which reads back deep-equal (`toStrictEqual`) to `toJSON()`; nested
  preloads (to-one, to-many, `null`, a selected shape); embeds; an override at a nested
  level; the sign-up case, for the changeset and for the row `repo.insertOrThrow` returns
  (over a fake driver: the row keeps `password`, its JSON does not); `.virtual({ json: true })`
  set and unset; both orders of `.virtual({ json: true })` and `.redact()`; a changeset with
  `bigint`, bytes, dates, hidden fields, nested embeds and associations.

### Part 3: `Json<T>` and `JsonReturn<F>`

- `packages/core/src/schema/json-types.ts`, type-only, exported from `egon-orm`: `Json<T>`
  and `JsonReturn<F>`, `Json` of `F`'s return type unwrapped from a promise (keeps `null`;
  not the built-in `Awaited`, see review round 1).
- Every row type carries a type-only marker of its fields' builders (`RowMarker<F>`, a
  declared class with the optional method `"~fields"`, which a spread or a rest copy leaves
  out of its type); `Loaded`, `LoadedUnchecked` and `LoadedAs` carry
  `PreloadMarker<P>` (`"~preloaded"`), the preloaded associations as an object type
  (`{ readonly author: true; readonly comments: true }`). Nothing exists at run time.
- `Json` of a row: the fields whose `json` flag is true, mapped as `toJSON` maps them (a
  virtual `{ json: true }` field is optional, since it is unset on a row that was read);
  exactly the preloaded associations, recursively, a nullable `belongsTo` staying `| null`;
  no getters or methods. A row type with its own `toJSON` is `Json` of what it returns.
  Anything else follows `JSON.stringify` (dates, values with `toJSON`, `undefined`, functions
  and symbols dropped from objects and `null` in arrays, a plain `bigint` is `never`).
- `repo.preload` (`repo.ts`, types only) keeps the marker of rows that already had preloads
  and merges the new one, so `Json` of `repo.preload(Post, withAuthor, "comments")` has both.
- Type tests (`json-types.test-d.ts`): every rule above; the preload forms (string, array,
  nested object, `true`); a row with more preloads where fewer are expected (and the
  negative); a getter returning a row is left out; a query's result; one `as const
  satisfies PreloadSpec` spec used by the query and the type; `JsonReturn` of a function
  returning a row, an array, `| null`, a write's `Result`, an object of rows, and
  `errorMessages()` (equal to `ErrorMessages<typeof User>`).

### Part 4: error trees typed by field (the exact form)

- `Changeset<S, New, E>`: a third parameter `E` (default `never`) collects the error keys
  that are not fields: `validateConfirmation("password")` adds `"passwordConfirmation"`,
  `addError("captcha", …)` and `validateAcceptance("terms")` add their literal key (field
  names still autocomplete; a field name adds nothing).
- `errorMessages()` returns `ErrorMessages<typeof cs>` and `traverseErrors(cs, fn)` returns
  `ErrorTreeOf<typeof cs, T>`: `TypedErrorTree<S, E, T>`, one optional key per field,
  association (known to the types), extra key and `$base` (where `validate` puts issues
  without a field); an embed or association holds the nested tree (`T[] | Tree[] |
  { $errors, $items }` for to-many, `T[] | Tree & { $errors? }` for to-one), as the run time
  builds it. A changeset made from a row alone (its associations unknown to the types) has
  its fields typed plus any other key; a changeset of an unknown schema keeps `ErrorTree`.
- **Extra keys survive a write.** The repo's write signatures type the returned changeset
  as `Changeset<S, N>`, which drops `E`. So the tree also includes `ExtraErrorKeys<S>`: the
  extra keys of the schema's own static `changeset` function, read from its return type.
  `result.error.errorMessages()` after `repo.insert(User.changeset(User, input))` therefore
  has `passwordConfirmation`. (A changeset made by another function loses its extra keys
  through the write; see Requests.)
- Exported for clients: `ErrorMessages<C>` (a changeset type or a schema class),
  `TypedErrorTree`, `ErrorTreeOf`, `ExtraErrorKeys`.
- `E` is recorded by a type-only member `"~errorKeys"`, typed as a method parameter so that
  it is compared both ways: a changeset with extra keys is accepted wherever a changeset of
  its schema is (`repo.insert`, `repo.update`; tested). The methods that add keys return
  `WithErrorKey<this, K>`, and `errorMessages` takes a `this` parameter; declaring them with
  `Changeset<S, New, …>` made TypeScript compare `Changeset<S, New>` structurally inside the
  class and broke `merge` and the nested-changeset helpers.
- Type tests (`error-messages.test-d.ts`): the keys (`keyof` of the tree), a typo is a
  compile error (on the tree and on an `ErrorMessages` literal), nested trees (association,
  embed, to-one), extra keys from each method, from the schema's changeset after
  `repo.insert`, a changeset with extra keys passed to `insert`/`update`, row-only and
  schemaless changesets, `traverseErrors`.

## Decisions

- **Markers are string-keyed (`"~fields"`, `"~preloaded"`), not `declare`d unique
  symbols** (the spec's wording). With a symbol, any user module that is compiled with
  `declaration: true` and exports an inferred type that contains a row's properties (a
  spread `({ ...user })`, a rest `const { email, ...rest } = user`, a `repo.preload`
  result) fails with TS4023/TS4058, "has or is using name 'FIELDS' … but cannot be named":
  declaration emit cannot add the import a computed key needs, and exporting the symbol
  (even as a value) does not help. Reproduced in `examples/blog` before switching. String
  keys follow the codebase's existing type-only members (`"~field"`, `"~embed"`,
  `"~foreignKey"`, `"~fromRow"`, `"~query"`); the cost is that an editor lists them, at the
  end, after typing `.`.
- **The row type does not declare `toJSON()`** (see "Needs the owner's decision"): `Json<User>`
  reads the markers instead.
- `Json` of a row's virtual `{ json: true }` field is optional: the field is `undefined` on a
  row read from the database, and `JSON.stringify` leaves it out.
- A custom type's value is mapped as a field value (a `bigint` to a string, bytes to
  base64, a `toJSON` called, objects walked), not passed through unchanged as the table
  says: unchanged, a custom type over `bigint` would make `JSON.stringify(row)` throw, and
  the types cannot tell a custom type from a built-in one. The conversion is chosen by the
  type's storage kind (`db.kind`) and checks the value, so a custom type stored as
  `timestamptz` is mapped as a timestamp when its value is a `Date`.
- Values that are not fields (a preload's selected shape) follow `JSON.stringify` exactly,
  `bigint` included (it throws), as `Json` says (`never`).
- A row's JSON includes every own property after its fields (the preloaded associations)
  without asking `assocs()`: a subclass's prototype holds the base class's metadata, whose
  `assocs()` does not know the subclass's statics. A property a user adds to a row is
  therefore written, as before; `Json` does not list it.
- `$base` is a key of every typed tree (`validate` reports issues without a field there).
- The schema's own `changeset` function supplies extra keys (part 4 above). This is
  inference from the user's own code, not new behaviour, but it is the one place where the
  types reach for a function the user did not pass; the alternative is the repo request
  below.

## Needs the owner's decision

1. **Typing `row.toJSON()`.** TypeScript cannot give the row type a `toJSON(): Json<this>`
   and keep the two things the guide promises:
   - *A schema class may define its own `toJSON`* with another return type. A subclass
     member must be assignable to the base member; `this` stays abstract in that check, so
     no declared return type (conditional, generic, `this`-indexed: all tried) accepts an
     override with a different shape, and reading the override's type back from the
     declaration is circular (TS2577).
   - *A plain object fits where a row of an embedded schema is expected*: `change(User, {
     address: { street, city } })`, `putEmbed`, `insertAll`, `PutObject`. A required
     `toJSON` member on the row type breaks all of these (the conformance and nested tests
     failed with TS2741 when it was declared).

   So the row type has no `toJSON` (as on `main`), and `Json<User>` says what it returns.
   Options:
   - **(a) as shipped**: no typed `toJSON()`. A React client component gets
     `JSON.parse(JSON.stringify(user)) as Json<User>`, or a server function's return typed with
     `JsonReturn`.
   - **(b)** declare `toJSON(): Json<this>` on rows, and accept that overrides must return the
     same shape and that embedded rows can no longer be given as plain objects without a
     change to every input type that takes one (changesets, puts, `insertAll`).
   - **(c)** a typed free function (for example `toJson(row): Json<typeof row>`), which the
     spec's "Out of scope" (`toPlain`) seems to exclude.
2. **Extra error keys through the repo** (part 4): keep `ExtraErrorKeys<S>` from the static
   `changeset` function, or make the repo's write signatures return the changeset type they
   were given (Requests), or both. The reviewer recommends the second and dropping the
   fallback, which also removes two defects of the fallback: it types the extra keys for
   every changeset of the schema (a login form's `cast(Account, params, ["email"])` has
   `passwordConfirmation`), and naming `ErrorMessages<typeof Loop>` inside `Loop`'s own
   unannotated static `changeset` is circular (TS7023, TS2502). On hold; not changed.
3. **String-keyed markers** (`"~fields"`, `"~preloaded"`) instead of the spec's declared
   unique symbols (see Decisions for why: TS4023/TS4058 in users' declaration emit). Their
   visible effects: editors list them after `.`; `keyof User` includes `"~fields"` (the
   test `keyof Every` = `FieldNames` had to exclude it); `Required<User>` and
   `Record<keyof User, string>` require the key; `z.infer` of `toZod(S)` equals `Row<S>`
   without it; hovers of query results show `PreloadMarker<…>`; `Changeset` lists
   `"~errorKeys"`. On hold; not changed.

## Review round 1 (PR #60)

- **TS2589 in `JsonReturn`** (blocker). The cause is the built-in `Awaited`, not `Json`: on
  `main`, `Awaited<Promise<User>>` followed by `Awaited<Promise<Loaded<typeof Comment,
  "post">>>` already fails with TS2589 (probably because `Awaited` asks whether the loaded row has a `then`
  method). `JsonReturn` now unwraps a promise with its own one-level `Resolved`, inferred
  from the return type. `Json` itself was also flattened: a row reads its fields' value
  types and flags from the builders' `"~field"` member instead of inferring against
  `FieldBuilder`, and one mapped type per row replaces three. New tests, each a program of
  its own so that nothing warms the caches: `packages/core/src/json-return-cold.test-d.ts`
  (the reviewer's snippet; `vitest` checks it with the other type tests, so it is cold only
  when compiled alone, which was done by hand) and `examples/smoke/types/json-return.ts`,
  which `pnpm smoke` now compiles against the packed packages in a second `tsc` program.
  Both fail with TS2589 when `JsonReturn` uses `Awaited` again (checked).
- **Integer-like association names** (regression): a row's `toJSON` skips its fields by
  name (a set in the JSON table), not by position. Test: an association `"2024"` with a
  redacted field.
- **`Json` of a copy**: `RowMarker` is now a declared class with an optional method, which
  spread and rest leave out, so `Json` of `{ ...user }` and of a rest copy follow
  `JSON.stringify` (secrets included, `bigint` as `never`). `Json<Omit<User, …>>` still
  describes the row: a mapped type keeps every member. Pinned by type tests; a "Good to
  know" line is in the recipe and requested for the guide. `PreloadMarker` stays a property
  (two methods would not merge when `repo.preload` adds a second marker); `Json` of a plain
  object ignores the `"~preloaded"` key. `RowSchema` (changesets of a row) skips `~` keys.
- The `JsonReturn` and `fieldConverter` examples compile (`getByOrThrow(query, { id })`;
  the possibly-`undefined` field handled), and so does `rowToJSON`'s (`JSON.stringify(user)`;
  `user.toJSON()` is not in the row type). All the TSDoc examples this step added were
  compiled in a scratch file, then the file was removed.
- `.virtual()` refuses option keys other than `json`.
- `MODEL` is defined once, in `schema/model.ts`.
- `omitRedacted` is removed (it was only re-exported from `internal/`), with its tests.
- Recipe: the Body column is filled in; a body that is not JSON is a 400.

## Known gaps

- `Json` of a non-row object type maps its declared properties: `Json<Map<…>>` and
  `Json<Set<…>>` list `size`, which `JSON.stringify` does not write (it writes `{}`).
- `toJSON` on cyclic data throws `RangeError` (stack overflow) where `JSON.stringify`
  throws `TypeError`. Rows from the repo are not cyclic.
- A row's `toJSON` calls `Object.keys(this)` once per call to find its associations, as the
  old one did (and checks each key against a set of the field names); everything else comes from the precomputed table. No benchmark was run
  (deferred to step 19).
- A changeset made from a row alone (`change(post)`) has its fields typed in the tree and
  accepts any other key, because its associations are not known to the types.
